Job Hunting Assistant：多站点职位抓取与 LLM 匹配 pipeline

找工作意味着要在 LinkedIn、Indeed 和 Glassdoor 上反复阅读同样的职位，而每个站点都有自己的搜索、 自己的筛选器，以及对"一个职位"是什么的不同理解。Job Hunting Assistant 是我为自己的求职搭建的工具： 一个 Chrome extension，通过我已登录的会话抓取这三个站点；一个 FastAPI 后端，把每条职位存两次——一次按 站点原本的形态，一次按单一的 canonical shape；以及一个 React 控制台，用来搜索、阅读，并让整套系统无人值守地 运行。自八月起，第二个仓库 filter-matcher 读取这张表，把它变成一份值得投递的短名单。 两者都在持续开发中；本页的可交互图示运行的正是后端和 extension 所运行的同一份代码。

    它是什么

    三个进程加一个数据库。extension 在真实浏览器会话内完成抓取：content script 读取各站点的职位列表， 通过站点暴露的任意接口获取完整描述，然后把每条职位交给 service worker，由它 POST 到后端。 后端负责摄入、回传、通过 WebSocket 流式推送扫描进度，并持有让 extension 能够独自运行数天的状态。 控制台有四个页面：搜索什么、职位列表、带调试追踪的扫描日志，以及 auto-scrape 仪表盘。 一切都在本地的 Docker Compose 下运行；没有云端，除了我之外也没有别的账号。

    三个站点，三种不同的数据接口

    三家招聘站都没有为此提供公开 API，而且每一家都把完整职位藏在不同的地方。每个站点的抓取器都是一组 独立的 content script，而每一个抓取器里最有意思的工作，都是找到那个返回结构化数据、而非需要解析渲染后 HTML 的接口。

    LinkedIn 的职位页面由一个名为 Voyager 的内部 REST API 渲染。页面自己的 JSESSIONID cookie 同时充当 CSRF token，所以 content script 从 document.cookie 中读出它，然后用站点自身使用的同一个 decorationId 请求 /voyager/api/jobs/jobPostings/{id}，就能拿回完整的 WebFullJobPosting 实体 JSON——标题、描述、薪资、以枚举 URN 表示的工作地点类型、已解析为实体的行业。最多尝试两次， 遇到 429、403 或 LinkedIn 非标准的 999 就放弃这条职位，而不是一路重试到被封。

    Indeed 把搜索结果作为嵌入页面的"mosaic"数据块下发，其中包含职位 key 和卡片级字段； 描述则来自 apis.indeed.com 上的一个 GraphQL 端点，需要在请求头里带上页面的 API key。 查询精确请求模式中存储的那些字段——属性、地点、带计薪单位的薪酬、语言——因此来源表行就是 API 的 原始回答，而不是对它的解析结果。Indeed 的脚本前后经历了六种抓取策略才定下这一种；文件至今仍叫 rate_strategy.js。

    Glassdoor 最为混乱：列表页有时带一个 __NEXT_DATA__ 块，有时只有 JSON-LD 的 JobPosting 模式，而两者对薪资来源的说法并不一致。曾经每一次 Glassdoor 详情抓取都失败——每次扫描都是零行——诊断结果来自一条 DevTools 日志：请求发向了一个地区子域 （fr.glassdoor.ca），而页面本身位于 www.glassdoor.ca，于是浏览器把它当作 跨域请求拦截了。把请求固定到页面自身的 origin，就是全部的修复。

    关于抓取。这是个人工具，并且刻意保持这一属性：它在我自己的浏览器里、用我自己的 登录运行，节奏像一个人在滚动页面——每次滚动间隔两到四秒，每次扫描间隔三十秒——每个周期开始前都会 探测各站点的会话状态，一旦某个站点返回人机验证就立即停止，而且它收集的任何内容都不会离开我的机器。 它存在的意义是让我把每条职位只读一遍而不是三遍。它不是产品，不会二次分发数据，我也不会把它当作 其中任何一种来运行。

    存两次：站点的形态，和我们的形态

    模式的第一个版本只有一张按 LinkedIn 形态设计的表，并试图把 Indeed 和 Glassdoor 塞进去。塞不进去， 最后控制台读的是一张空表，而真实扫描却写到了别处。七月的重建把这种拆分变得明确。每次摄入都在一个 事务里写两行：一行来源表记录，写入 linkedin_jobs、indeed_jobs 或 glassdoor_jobs——只追加、不做 canonical 转换、忠实于站点原话，并以 JSONB 保存原始载荷——以及一行 canonical 记录，写入 scraped_jobs：27 列、单一形态，控制台和未来任何消费者都能直接读取， 无需按站点做连接。

    所有 canonical 转换逻辑都集中在 projection 模块，它遵循三条经过一次真实扫描才校准好的规则。NULL 表示网站 没有说。绝不是"否"，也绝不是默认值：Glassdoor 没有远程布尔字段，所以当它列出远程工作类型时 remote 为 true，否则为 NULL——绝不会是 false。 带优先级的封闭词表。employment_type 是七个 token 之一；一条同时标注 Full-time 和 Part-time 的职位会得到 FULL_TIME，另一个标签只保留在来源表行上。 未知值触发警告，已认可的空操作值不触发。表从未见过的 token 会记录一条警告，词表正是 借此从线上数据自我修正；而站点回答 OTHER 是一个正确答案，它映射不到任何东西并保持沉默， 因此不会淹没真正重要的警告。 

    # projection 模块唯一一处明知比网站所说断言得更多的地方。
def _indeed_workplace_type(remote_location: Any) -> str | None:
    """Not a tri-state pass-through: False becomes ONSITE, an assertion Indeed
    did not quite make. Indeed cannot express hybrid, so a hybrid posting is
    recorded ONSITE — accepted so on-site filters return Indeed results at all.
    Read ONSITE here as "not remote", not as confirmed on-site."""
    if not isinstance(remote_location, bool):
        return None
    return "REMOTE" if remote_location else "ONSITE"

    其中两个 token 来自数据，而非设计。筛选列上线后的第一次扫描，为 Indeed 的"Permanent"记录了 projection_unknown_employment_type，为它的"EXTRACTION"记录了 projection_unknown_salary_source。Permanent 是任期维度，不是工时维度——长期兼职是存在的—— 所以它成了一个独立 token，优先级排在工时类 token 之后，常见的"Full-time, Permanent"仍然得到 FULL_TIME。EXTRACTION 表示 Indeed 从雇主自己的描述中解析出了薪资，因此算作雇主披露。 这两个决定都写在模块注释里，并附有促成它们的那次扫描的日期。

    流程抓住的陷阱。摄入使用 ON CONFLICT DO NOTHING，所以 canonical row 永远不会被重新计算。LinkedIn 工作地点修复之后，仪表盘显示"LinkedIn workplace = 0"，看起来像是一次 回归。把已存储的载荷重放一遍 projection，得到 REMOTE 180 / HYBRID 123 / ONSITE 76——代码是对的，旧行只是 过时了，而且会在一个 shelf life 内自行痊愈。区分这两种情况的方法——先重放，绝不重扫——现在写在该功能的 快速上手指南里。

    过期管理：让 append-only 存储保持有界

    各来源表按约定是 append-only 的，但一个连续运行数天的抓取器不能让表无限增长，而一条职位信息也只在 仍然开放时才值得保留。所以整个存储只有唯一一条删除路径，而且刻意做得很简单：当 NOW() > scrape_time + shelf_life 时删除该行。shelf life（保留期）是一个全局单值—— system_settings 表中的 shelf_life_days，默认 7——因为没有任何运维上的理由 让 LinkedIn 的职位比 Indeed 的活得更久。accessor 会对该值做类型强制和 clamp，遇到任何畸形输入都回退到 7，这样一个被弄坏的设置只会退化为安全默认值，而不会让 cycle 崩溃。 

    # backend/auto_scrape/auto_expiration.py
days = await get_shelf_life_days(db)                      # 来自 system_settings，默认 7
for table in ("linkedin_jobs", "indeed_jobs", "glassdoor_jobs", "scraped_jobs"):
    result = await db.execute(
        text(f"DELETE FROM {table} "
             f"WHERE scrape_time < NOW() - make_interval(days => :d)"),
        {"d": days},
    )
    deleted[table] = result.rowcount or 0
return {"deleted_per_table": deleted, "shelf_life_days": days}

    有三个细节支撑着这个设计。canonical table 用同一个 predicate 过期，而不是顺着键去追。 scraped_jobs.source_row_id 指向三张不同的表，所以不可能存在 foreign key——因此也不可能有 ON DELETE CASCADE。取而代之的是，ingest 把来源行的 scrape_time 逐字节原样复制 过来，两张表选出的是完全相同的集合，四个 delete 在同一个 transaction 中执行；一个 smoke test 守护着这次 复制，因为一旦回退成新取的 now()，边界处的 canonical 行就会成为孤儿。间隔是一个 bound parameter。这个值可以由用户在 console 中编辑，所以它经由 make_interval(days => :d) 传入，由数据库做类型检查，绝不做字符串插值。它在每个 cycle 里第一个运行。当 extension 完成一个扫描矩阵后，会通过 Redis 发布一次唤醒（APScheduler 作为 fallback），post-scrape orchestrator 认领该 cycle，把过期清理作为唯一阶段运行，并把 deleted_per_table 记录到 cycle 行上——于是 dashboard 能显示每个 cycle 删掉了什么。

    这条规则被写进了数据模型的“宪法”，作为来源行仅有的两种允许 mutation 之一（另一种是单向的 matched 翻转）。它的局限是明说的，而非藏起来的：过期清理不理会 matched， 所以一条从未被处理的职位会和其他行一起老化掉；没有逐行 TTL，所以“把这条留到下个月”目前还无处安放， 已预留给一份单独的用户兴趣记录；而调低 shelf life 会在下一个 cycle 一次性批量生效。这也解释了上面提到 的过时行行为——在旧 projection 下写入的 canonical 行永远不会被重新计算，但它也永远不会比一个 shelf life 更老，所以一次 mapping 修复会在一周内传遍整张表。

    在下游，filter-matcher 以自己的两次清扫呼应了同一思路，在每次运行开始时执行：shortlist 条目在最后一次写入 30 天后过期；audit 行在上游职位消失时被剪除——用的是一次 LEFT JOIN 检查，而不是 cascade，因为该服务从不持有指向 JHA 各表的键。永远不会被剪除的是运行记录中的计数， 所以即使背后的行已经老化掉，一次运行依然可以被检视。

    运行 orchestrator，一次一个周期

    来自 extension/background/auto_scrape.js 的 probeSiteSession、 preCycleCheck、自动暂停计数器和 scheduleNextCycle，原样移植。 设定每个招聘站的探测会返回什么，按下运行，观察状态行的变化。

      两条值得亲眼看看的规则。单纯的 403 被视为限流，而不是人机验证——只有验证挑战 URL 或可识别的验证 正文才配得上那个标签，因为人机验证需要一个人来处理，而限流只需要耐心。而 5xx 或 fetch 抛出异常会被 视为在线：招聘站宕机并不能证明我的会话已经失效，若因此暂停，每当某个站点状态不佳一分钟， orchestrator 就会卡住。把后端设为"离线"并连续运行三次，就能看到自动暂停。

      让 service worker 老老实实

      Manifest V3 的 service worker 随时可能被 Chrome 杀掉，所以一个要连续运行数天的 orchestrator 不能把状态放在 内存里。每个周期一开始就向后端的状态行写入 cycle_phase: scrape_running，结束时——在 finally 里——把它写回 idle。worker 还每 30 秒轮询一次那一行，只有在阶段不是 运行中且不存在闹钟时才重新设置自己的闹钟，正是这一点阻止了重启后的 worker 在第一个周期之上再叠一个 周期。状态行还带有一个含实例 id 的心跳，这样当同一个五分钟内有两份 extension 同时存活时，仪表盘能发出警告。

      那些更细小的规则来自观察它如何失败。连续的 pre-check 失败会让 orchestrator 自动暂停，而不是无限重试。一个在三十秒内 结束、且没有任何成功的周期会得到五分钟的冷却，因为"什么都没成功，立刻再试"恰恰是招聘站会封禁的模式。 在优雅退出和 worker 启动时，任何看起来像招聘站抓取的弹出窗口都会被关闭，这样僵尸弹窗就不能继续抓取， 也不能把自己挂到错误的运行日志上。进度会镜像到后端并通过 WebSocket 扇出，因此在一次运行进行期间， 控制台的扫描页面无需轮询就能实时更新。

      长时间运行才能发现短测试找不到的 bug

      orchestrator 四月底的第一次十小时 soak test，是一份问题清单。一个从未被任何代码清除的 config_change_pending 标志，让 255 个周期里有 254 个中止。每一个 HTTP 403 都被归类为人机验证，于是 Indeed 因为其实只是限流的问题被连续挂起了 191 次探测——这就是上文那条规则的 由来：单纯的 403 意味着耐心，而不是需要人。从"决定启动一个周期"到"记录周期已启动"之间有三十秒的窗口， 导致一小时内有十二个周期启动，三个弹窗同时抓取 LinkedIn；把 cycle_phase: scrape_running 作为第一行写入，把这个窗口缩到了大约五十毫秒。而来自更早周期的 僵尸弹窗把 207 条 Indeed 职位归到了一份 LinkedIn 运行日志名下，这就是为什么启动时现在会关闭任何看起来 像抓取的弹窗。修复后的五小时验证运行完成了九个周期中的八个，抓取 984 条 LinkedIn 和 65 条 Glassdoor 职位，归属错误为零。

      如果面试时要讲一个，我会讲第 455 个周期。仪表盘报告九次扫描零次成功——同时却有 949 行新的 LinkedIn 数据。原因是一个五分钟的"陈旧扫描"清理阈值，对完全健康的 33 分钟 LinkedIn 扫描（39 页、915 条职位） 误触发，随后一次状态写入又把 failed 翻回 completed，却把错误信息留在原地。 它从 5 月 4 日起就一直在悄悄触发。修复是两行代码；笔记里的教训只有一句：可观测性撒谎比运行时 bug 更糟。修复后的第 481 个周期以九次全成功摄入了 1,306 条职位。

      另外两个较小的问题，对代码的影响远超其表面大小。摄入曾用 scalar_one_or_none() 按描述哈希 查找职位，而由于重复发布和 ATS 模板会合理地共享同一个哈希，百分之六到十的 LinkedIn 摄入返回了 HTTP 500；换一个方法调用就把每次扫描的新职位数从大约一百提升到大约 240。而 extension 最初的 setInterval 轮询器在 Chrome 因三十秒空闲而挂起 service worker 后干脆死掉，于是"扫描" 在你碰一下标签页之前什么都不做——这就是现在一切都由 chrome.alarms 驱动的原因。

      开发方法：spec-first，与 Claude Code 协作

      前四个月是以通常的方式、让 AI coding agent 参与其中构建的，到七月时，结果呈现出这种方式典型的形态： 大量能跑的代码、前端里三套样式系统、一条状态机藏在可空列里的匹配 pipeline，以及一份描述着已不复存在的 系统的 README。随后的重建是一次有意为之的 spec-driven development 练习，使用 GitHub Spec Kit，由 Claude Code 担任实现者——而起点是从未用过它。

      每一次变更的循环都相同：constitution → specify → clarify → plan → tasks → analyze → implement。constitution（宪章）是一份简短的文档，写明项目的真实规则——所有模式变更都经由 Alembic、来源表只追加、dual-write 必须原子、后台工作在新会话中进行、smoke test 即行为契约、外科手术式地修改。 在改动任何东西之前，agent 先为五个模块按其实际行为撰写了 as-built spec（竣工规格），每份都附带一次 对照源码的验证和一份优化待办。然后五份功能规格把系统从那时带到了现在：仅搜索拆分、Glassdoor 修复、 统一表、前端重建（94 项任务）和筛选列（48 项任务）。配套服务也以同样方式从一个空仓库建起：自己的 constitution、 一份 146 项任务的规格，以及六份领域检查清单——边界、成本、dedup、保真、完整性、需求——它们的处理结论 以带日期的澄清记录写在规格本身之中。

      对于怀疑这种工作方式的人，我想说的是：规格正是工程判断所在之处，工作也正是转移到了那里。projection 模块的 词表在规格中被标注为"推理所得，非观察所得"，并要求在功能关闭之前审阅一次真实三站点扫描的警告—— 这次审阅发现，agent 编写的 LinkedIn fixture 假设的是本地化标签（"Remote"、"Hybrid"），而线上载荷发送的 是裸枚举 URN。用模块自己的话说，这个 fixture 是虚构的；流程的设计就是为了让虚构无法上线。前端重建在每项 任务前都设了真正的 tsc 和 ESLint 门禁，包括一条自定义 lint 规则，禁止从 UI 调用 "消费即清除"的 /extension/pending* 路由，因为那些路由是未来某个页面必然会踩进去的陷阱。

      我要求 agent 遵守的工作规则写在两份 constitution 里，它们都来自吃过的亏。读条款，不读摘要。用真实 数据验证，而不是推断——代码审阅看不见状态，只有查询能看见，而且不止一次，agent 报告"实现完成"的 变更根本没有进入正在运行的容器。不允许空洞的绿色——被跳过的断言就是失败，因为一个从未运行 过的对勾会终结对 bug 的搜寻。限定范围——在另一个仓库里发现的腐坏要在规格中标记，而不是顺手 修掉。而在任何大改动之前，先问。匹配声明机制的方案在实现之前，对照线上仓库做了六轮冲突扫描—— 13 个问题，然后 8、3、2、2、0——这 28 个发现中的每一个，在文档里修都比在代码里修便宜。

      agent 做了什么，我做了什么。Claude Code 编写了两个仓库里几乎全部的代码、规格，以及 我为本页所参考的笔记。我设定方向，撰写并批准 constitution，做出规格中记录为澄清项的每一个设计决定：我否决了 "更纯粹"的声明设计，选择了更简单的表内列方案；我把 agent 构建的八十行失败摄入重放缓冲区换成了十行的 停止并上报，因为卡片仍然在来源页上，明天的扫描自会把它们捡起来；PERMANENT 之所以是一个 token，是因为 我判定它属于任期维度。我运行了十小时和五小时的 soak test，阅读了真实扫描的警告，必要时用 SQL 强制 停止失控的周期。本页记录的 bug 都是我在自己的求职过程中运行它时发现的。我认为这就是 2026 年诚实的 分工，我宁可把它写明白，也不愿让读者去猜。

      离开又归来、自成一个服务的那一半

      七月之前，JHA 还负责对职位 dedup 并与我的简历匹配：三轮 dedup（元数据门禁、描述门禁，然后是精确哈希和 TF-IDF 余弦相似度的重复检测）和一条四阶段匹配 pipeline（CPU 提取、对年限、薪资、学历和签证的硬性门禁、 一次 CPU 预打分、可选的 gpt-4o-mini 重打分）。它能工作，但 as-built spec 仍然论证了应当移除它： 它的状态机隐含在可空列里，它只针对旧的 LinkedIn 形态表运行过，而且没有一个测试覆盖它的资格规则。 仅搜索拆分把它整个删除，canonical table 得到了一个 JHA 内部任何代码都不会设置的 matched 标志。

      filter-matcher 是它在八月回归的地方：一个独立的仓库，有自己的 constitution。它是一个按需运行的 CLI——python -m filtermatch run [--limit N] [--cpu-only]——只读取 scraped_jobs，用 WHERE matched = FALSE 认领一批职位（在一个事务里翻转 canonical row 及其来源表的原始行，这是它对 JHA 数据做出的唯一写入），然后把每条职位推过严格按最便宜优先 排序的各个阶段：五项个人偏好、一次完整性检查、字段门禁、重复检测、CPU 技能提取与门禁，然后是 任何 AI 调用之前的 coverage banding。覆盖率低于 0.50 的直接拒绝，不花一个 token；恰好 1.00 的作为 cpu_perfect 进入短名单；只有介于两者之间的模糊区间才交给模型。它写入五个自己的存储—— 短名单、排除审计、黑名单重入台账、技能候选表和运行记录——每次运行结束时都要对账：认领数必须等于 入围数加排除数加异常数，否则该次运行记为失败。 

      # pipeline.py — 为什么完整性检查要在语言门禁之前运行。
# 实测，2026-08-07：langdetect 对两个字符返回匈牙利语，置信度 0.999994；
# "Job posting." 返回他加禄语，置信度 0.999996。短文本
# 并不会产生低置信度——它会对错误的语言产生虚假的高置信度。
# 所以一条被截断的职位若先到达语言门禁，会被记录为
# (field_gate, language_mismatch) 并附上一个凭空捏造的判决，
# 而不是它实际所属的 (cpu_gate, incomplete_posting)。

      成本纪律是一条含七项编号规则的 constitution 原则，整个设计围绕它们展开：任何模型调用之前先过廉价门禁；只有 模糊区间才会消耗判断类 token；每份职位描述只压缩一次成 120–200 词的 standardized_jd， 输入 token 减少约 70%；prompt 按静态内容优先排序，让服务商的 prefix caching 为重复的那一半打折；技能由 CPU 别名词表提取，绝不交给模型。规格中的一个十五格结果矩阵管辖覆盖率区间、模式和 AI 结果的每一种组合—— 十四种可达，一种被证明在结构上不可达——短名单还记录每条记录由四种决策方法中的哪一种产生，这样，用 规格自己的话说，一份满是 cpu_tiebreak 的短名单就能被识别为一次悄悄丢失了 AI 的 AI 运行。

      这份规格有 104 条需求、25 条成功标准和 43 条记录在案的澄清，它所要求的真实数据审阅证明了自己的价值。 规格假设的计薪周期词表是 YEARLY；线上表里写的是 ANNUAL，28% 的职位本会 悄无声息地变成"薪资不可比较"。Glassdoor 把技能列表写进了它的经验水平字段，所以一个看似合理的经验 门禁本会排除掉 56% 的语料。而设计中"大约一半的积压可以认领"的假设错在了另一个方向：全部 113 条线上 记录都可以认领。constitution 的第四条原则——误保留只多显示一张卡片；误丢弃则隐藏了一个真实机会—— 正是这些问题每一个都变成了"保留并计数"、而绝不是"排除"的原因。

      五次 migration，五套 smoke test 中的 184 个测试（所有 AI 路径都已 mock），以及 146 项任务中的 137 项已完成。 未完成的九项是诚实的：三项被真实数据阻塞——服务在开发期间就已耗尽了所有可认领的职位（113 条中的 113 条），因此一次真实的 AI 模式运行、一份真实的 cpu_strong 短名单和一次真实的跨站合并， 都要等待下一次三站点扫描。构建它还暴露了一个值得记录的陷阱：它的技能候选 migration 与 JHA 自己的 017 号 migration 遗留的一张表相撞——7,976 行冻结数据，没有任何活代码使用它——修复是一次重命名，外加一条新规则： 每个存储的名称都要在 migration 时断言尚未被占用，这样下一次冲突就是一次有名有姓的中止，而不是一道谜题。

      不足之处

      Glassdoor 的 workplace_type 始终为 NULL，因为抓取器尚未捕获 remoteWorkTypes。projection 是正确的，一旦 extension 提供该字段就会立即填充——但如果某个消费者 用 workplace_type 而不是 remote 来筛选远程职位，就会悄无声息地丢掉整个 Glassdoor 语料。

      测试不对称。前端有 135 个单元测试；后端有四个需要运行中的 Compose 栈的 smoke test 脚本， 以及 projection 模块上的一个单元测试。projection 模块值得拥有一套像样的参数化测试，摄入路由也是。

      到处都是单用户假设。认证是一个 bearer token（dev-token），配置是一个 JSON 文件，orchestrator 状态是一个单例行。对于一台机器上的一个人来说全都正确，对于其他任何情形全都错误—— 只要它一直是一台机器上的一个人，这就没有问题。

      清单上的小事。GET /jobs 按 scrape_time DESC 排序且没有 次级排序键，所以分页边界可能重复一行；constitution 仍然逐个列举测试文件名，新增一个就会漂移；还有两项前端 检查（360 px 布局和未保存更改守卫）仍需要一个人在真实浏览器里验证。
