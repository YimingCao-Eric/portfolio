AI-news：按我的兴趣给全网排序的个人每日摘要

一个定时任务：从一份固定的 AI、硬件和游戏类信息源列表抓取内容，丢掉所有之前见过的条目， 把剩下的按兴趣画像排序，对排名靠前的一段做摘要，然后写出一页 Markdown——我每天早上读它， 而不是去刷 Hacker News。没有 app，没有服务器，没有 UI——这一页就是产品本身。

状态：进行中——5 个 phase 中的 phase 0 到 3a 已合并，外加一次完整的代码 review。骨架、端到端跑通的全部五个信息源、 带去重的 SQLite store，以及一次阶段间 review：提出 54 条发现、修掉其中 43 条，而 pipeline snapshot 一行未动。下一步是 phase 3b：带按主题配额的规则 ranker，然后是渲染出来的页面。开始于 2026-09-12 · 最近更新于 2026-09-15。

是同一条新闻吗？

来自 src/digest/store.py 的 canonical_url、url_hash 和 titles_are_near_duplicates，被原样移植成了 JavaScript——同一份跟踪参数列表、同样的 34 个 stopword、阈值 0.85 的 Dice coefficient，以及同一个数字守卫。改动任意一侧，观察判定结果。

两家媒体的两条标题

指向同一页面的两个链接

三个值得一试的操作。第一个标题预设的 Dice 比值是 0.89——妥妥的重复——却仍被判为不重复，因为 4.5 和 4.6 是两个不同的数字 token；这个守卫就是"一条新闻"与"两次模型发布"之间的分界线。 第五个预设是已知的漏网之鱼："releases"和"released"是不同的 token，所以一条调换了语序的标题只得到 0.80， 就这样溜了过去——要修它需要 stemming（词干提取），而 v1 刻意不做。在 URL 一侧，第二个预设说明了为什么 source 不在剥除列表里：?source=trending 和 ?source=likes 是 Hugging Face 上两个不同的列表页，若剥掉这个参数，两者就会被合并——没有新行、没有日志、也没有任何办法察觉。 两侧各自的最后一个预设，是五个信息源跑起来之后线上数据库抓到的第一个跨信息源重复：同一篇论文分别出现在 Hugging Face 和 arXiv 上，两个 URL 哈希不同，一条标题完全一致。

它是什么

一个带四个子命令的命令行程序——digest fetch、rank、render、 run——刻意分开，好让排序逻辑可以反复迭代而无需重新抓取。它读取两个 YAML 文件： sources.yaml（拉取哪些 feed、各自的权重，以及每个信息源的 fetch_limit）和 interests.yaml（带关键词的主题、按主题的配额、反主题、硬性规则）。它学到的一切都落在一个 SQLite 文件里；输出是 digests/YYYY-MM-DD.md。五个信息源，全部上线——Hacker News、GitHub Trending、 Hugging Face daily papers、一组六个 AI 实验室博客 feed、arXiv cs.AI / cs.CL / cs.MA——以及一条硬规矩：pipeline 端到端跑通之前，绝不加第六个。

pipeline 分七个 stage，能写成纯函数的都写成纯函数，每个 stage 都在自己的模块里，配一行契约： 

fetch → normalise → store → rank → summarise → render → deliver

adapters/    only fetch and map to Item. No scoring, no DB, no LLM.
store.py     only reads/writes SQLite. No business logic.
rank.py      pure: (items, profile) -> scored items. No I/O.
summarise.py the only module allowed to call an LLM.
render.py    only turns selected items into text via a jinja2 template.

这套分层作为硬性约束写进了仓库的 CLAUDE.md——不用 web 框架、不用 ORM、不用 Docker、不用队列、 不经询问不加新依赖、测试里不许访问网络——正是为了让构建 phase 4 的 agent 无法重新翻案 phase 0 已经定下的事。

Phase 3a：先探测，再动手

剩下的四个 adapter 是凭对各家 API 的记忆写出规格的，所以这个 phase 从对每个端点逐一探测开始，然后才对着它写代码—— 凭空捏造不存在的隐患，代价和漏掉真实隐患一样大。brief 里的三条假设没能撑过探测。arXiv 的标题本来就是干净的： 270 条 cs.AI 条目里有 0 条带着 prompt 所警告的 arXiv: 前缀或内嵌换行，所以 normaliser 保留下来 作为对旧格式的防护，并用一个测试钉住这次测量，好让注释永远不会漂移成宣称一个并不存在的隐患。arXiv 的量是 估计的五倍——仅 cs.AI 就有 270 条，三个类别共 401 条。而且 38% 的 arXiv 条目是修订版：一条 replace 是某篇可能已经几个月前的论文的 v2，进入摘要时却像刚发布一样，所以 adapter 只保留 new 和 cross 两种 announcement，并用一个测试断言修订版占比超过 25%，这样一旦删掉 这个过滤器，测试会说明坏在哪里，而不是悄无声息。

模式比数字更要紧：两个官方 feed 都是新鲜的，四个镜像 feed 里有三个已经陈旧，而且全都是 格式良好的 XML。一个逐 feed 不可靠的镜像是最糟糕的形态，因为一个健康的 feed 对其他 feed 的状况毫无说明。 核查过的每一个替代方案都返回 404，所以镜像保留；三个死掉的 feed 换成了 claude、 anthropic_research 和 cursor——都新鲜，并且偏向 AI coding agent，也就是画像里权重 最高的主题——被撤下的那几个则以注释的形式留在 sources.yaml 里，附上实测的年龄，这样"Mistral 怎么不在？"就有了书面答案。随后一个 commit 把每个 feed 的陈旧阈值挪到配置里，紧挨着它的 URL，并把实测的更新 节奏写成注释，因为一个全局数字要么对慢 feed 狼来了，要么对快 feed 睡过头，而一个狼来了的警告会被无视。

两个只有线上运行才能抓到的缺陷

博客合集把整个历史存档都导了进来——1,824 条。不同于发布当前列表的 arXiv、Hugging Face 或 GitHub，这些 feed 提供的是好几年的历史（仅 openai_news 就有 1,193 条），而在 48 小时的 max_age_hours 之下，它们永远不可能被选中。一个 30 天的条目截止线，给出了任何可能被选中的条目 十五倍的余量：1,824 变成了 112。

这个修复本会悄悄毁掉陈旧度警告。一个陈旧了 112 天的 feed，在 30 天窗口内的条目为零，所以 在截止线之后测量陈旧度只会报告一句干巴巴的"0 items"——读起来像是安静的一周，恰恰丢掉了这个机制 存在所为的那个信号。现在最新条目的日期是在截止之前对全部条目计算的，并有一个测试断言这条备注说的是 stale 而不是 0 entries。这是项目里第四次出现同一种形态——两个各自正确的改动互相遮蔽—— 它变成了计划里一条常设的评审问题：对每一个过滤器，下游有哪个测量读取的是过滤后的数据，它需要的是不是 未过滤的版本？

什么时候零条目是个错误

当零意味着我们已经不再理解这个端点时，抛异常；当零是信息源真的可能处于的状态时，返回空。GitHub Trending 永远 有行，所以零就是选择器腐坏或者 403 的响应体，adapter 抛异常；精选论文列表同理。arXiv 返回空，但 feed 格式 错误时抛异常；博客合集逐 feed 返回空，但六个都一无所获时抛异常；Hacker News 直接返回空。逐 feed 的诊断信息 作为数据传递——对 adapter 契约做了一个小小的 drain_notes() 扩展，因为 adapter 不许写日志，而 Item 和 SourceHealth 都没法表达"成功了，但六个 feed 里有一个已经死了四个月"—— 并在 finally 里排空，好让六行失败记录在"所有 feed 全死"的错误中幸存下来。恰恰在出了问题的时候 丢掉诊断信息，正是这个机制所要防止的那种失败。

这个 phase 还在线上数据库里产出了第一个跨信息源重复：同一篇论文来自 Hugging Face 和 arXiv，两个 URL 哈希 不同，被 Dice 和数字守卫抓住了。没有实现胜出方——这个 phase 是为了观察——但有两条发现转到了 3b：两个 URL 都以同一个 arXiv id 结尾，所以一条提取 id 的规则能精确抓住每一对这样的重复，并且应该放在标题相似度之上， 而不是折叠进 canonical_url——在那里一次合并就是一次静默丢弃；而目前的胜出方是由配置顺序决定的， 那不算一个决定。

阶段间 review：十一个 commit，零新功能

phase 3a 往一条 pipeline 里加了四个 adapter，而这条 pipeline 的形态是在只有一个 adapter 时定下的，从没有人问过 这个形态是否还成立。所以在 ranker 动工之前，整个代码库沿六个维度做了一次评审——静默失败与可观测性、分层与 耦合、重复与 adapter 的形态、测试套件的健康度、词汇与错误分类体系、文档漂移——每条发现都归入三个桶之一： 在项目约束内可以改进的；约束本身在造成伤害的；或者约束在起作用、而显而易见的改进反倒是退步的。五十四条 发现：43 条已修复，10 条依据明确的触发条件推迟，1 条不予修复。七个修复主题，一个 session 一个。测试套件从 收集到的 178 个增至 242 个。

先搭安全网

在任何评审 session 开跑之前，先用一个 commit 建了一份 characterisation snapshot：对录制好的 fixture 跑真实的 fetch → store 组合，导出为 425 行排好序的记录，每条附带原始载荷的哈希。它对正确性不做任何断言—— 只断言这个组合没有移动——正因如此它才是重构可以被衡量的契约，覆盖了单元测试在结构上无法覆盖的东西：跨信息源 dedupe、每一条 dupe_of 的方向、四种日期格式汇入同一个 store。它的时钟从 fixture manifest 里 钉定，而不是一个常量，因为博客合集是按 now − 30 days 过滤的：把时钟冻住，第一次刷新 fixture 就会把 每一条都推出截止线之外，得到一份空空如也的 snapshot，而生成它的测试依然通过。它经历了一次模型拆分、六次重命名、 一次上限搬迁、一次注册表替换和一套新的错误层级，仍然逐字节一致——而为了让红色的测试变绿而重新生成它是被 禁止的，因为那等于一次删掉了证据的重构。

后果最严重的一条发现

所有信息源都可以失败，而进程仍然以 0 退出。连续七次全盘失败，本可以在什么都没交付的情况下满足 项目自己的"无人值守连跑七天"标准，而定时任务会自始至终显示为绿色。修复方式是从各个 outcome 读出一个 exit code——所有启用的信息源全部失败时为 4——而明确不是去收窄那个让一个死掉的 feed 不会中止整次 运行的 catch。紧随其后的一条：明文要求的"每个信息源一行"运行日志位于 INFO 级别，而默认级别是 WARNING， 所以 07:00 的定时运行会把它写到无处可寻。没有人会在 crontab 里敲 -v。

唯一一条针对约束本身的发现：CLAUDE.md 的完成定义要求 digest run --dry-run 能跑完， 而 run 是一个打印"not implemented"然后以 0 退出的桩——于是一个弄坏了所有 adapter 的改动，也 能一字不差地满足质量门槛。这比没有这一条更糟，因为它读起来像端到端验证，挤掉了 session 本会即兴补上的 检查。它单独落在一个 commit 上，而不是塞进某次重构里，因为埋在 diff 里的治理改动，对后来追问"门槛为什么 变了"的人是不可见的。

报告提议，diff 决定

review 文档是从各个 commit 的 git show 推导出来的，而不是从报告，而两者的比较是最有意思的结果。 每一条发现、每一个修复或推迟的决定都站住了。五条规定好的机制却没有：一旦代码在手，每一条都朝着更 保守或更具体的方向挪动了——其中两条是对指令而非发现的纠正，triage 建议的重命名会恰好重用相邻那条发现正在 移除的那个词。事实证明，从报告写出来的 triage 在方向上可靠、在机制上欠缺细节，而这些偏离之所以存在，只是 因为每个主题在被允许写代码之前都必须先提出计划。triage 得到的是一条注明日期的修正说明，而不是重写：它是 当时所作决定的记录，而那道差距正是有用的部分。

修复过程中发现的一些东西不在任何报告里，只在 diff 里。fixture 录制器把整个 Hacker News 的 URL 写死了， 所以一次配置改动就会让 snapshot 建立在一个生产环境已经不再使用的窗口上。一个抽取出来的日期 helper 差点把 格式错误的日期变成缺失的日期——条目还在，看起来什么都没丢，只是永远不会被排进去——它被一个为另一条发现 而写的测试抓住了。有一处编辑悄悄地从未生效，digest render 在整整一个主题期间把禁用的信息源 错标为quiet，因为测试直接调用了 helper 并传入了真实调用点所缺的那个参数；这变成了一条常设规则—— 一个自己提供参数的测试，证明不了调用方也提供了它。而作为最后一个主题的最后一步，把 README 里声称的 每条命令都执行一遍，找出了三处不实的说法，其中一处就写在同一个 commit 里。

六条发现被记录为不要改进的事项，因为显而易见的修复恰恰是退步：不要收窄 catch-all，不要把部分失败 变成非零退出，不要把 arXiv id 折叠进 URL canonicalisation，不要剥除 source，不要让四位数年份 豁免数字守卫，不要合并那三个 48 小时窗口。十条推迟项各自带着一个触发条件，写在将来动手的那个文件里——一条 docstring、一个常量、一句配置注释——而不是只写在一张要有人重读才会生效的表格里。

值得辩护的决定

大多数代码之所以存在，都是因为某个具体的决定，而每个 pull request 都记录了评审者应该追问的那些决定。 塑造了 store 的几个——它们全部经受住了阶段间 review，其中好几条还在它"不要改进"的清单上：

"新"意味着 digest_date IS NULL，而绝不是日期比较

最显而易见的查询——first_seen_at 落在今天的条目——错在两处。存储的时间戳是 UTC，而摘要的"一天" 是 America/Vancouver，所以当地 07:00 的一次运行对应 UTC 14:00，按日历日期比较会把同一个早上的条目劈到两个 UTC 日期里，天天如此。而且基于日期的查询会永久丢掉任何没跑成的那一天：笔记本休眠、Action 失败、周末出门。 取而代之，digest_date 一开始为 NULL，只有当条目被渲染进某期摘要时才盖章；漏跑一次之后自然会 自己补上。有一个测试专门跳过一天，并断言两天的条目都会回来。

Dice 而非 Jaccard——上面再叠一层数字守卫

在 0.85 的阈值下，Jaccard 对真实标题几乎够不到：七个 token 的标题多出一个词就已经贴在边界上，多两个词就 判为不同，于是这项检查看起来在工作，实际上几乎从不触发。Dice 让 0.85 保持有意义。但 Dice 单独使用有一类 误报，正好砸在这份摘要的题材上——RTX 5090 Super 与 RTX 5080 Super 得 0.875，两个只差一个 数字的模型版本或两篇 arXiv 论文也是如此。所以凡是含数字的 token 不一致的标题，无论比值多高，一律不算重复； 而且守卫用的是"token 里含有数字"而非 str.isdigit()，因为 7B、v2 和 gpt-5 恰恰是最要紧的 token，而它们没有一个是纯数字。一个名为 test_the_numeric_guard_is_load_bearing 的测试断言 5090/5080 和 4.5/4.6 这两对都得分高于阈值， 这样一旦删掉守卫，测试套件会准确说出坏在哪里，而不是悄无声息。

只剥除毫无歧义的跟踪参数

最初的 spec 把 source 和 utm_*、fbclid、gclid 一起剥掉。 这是错的：光秃秃的 source 是个普通的应用参数，huggingface.co/models?source=trending 和 ?source=likes 是两个不同的列表页，却会得到完全相同的哈希。这种失败是不对称且不可见的—— dedupe 用的是 INSERT OR IGNORE，所以第二条会被直接丢弃，没有新行也没有日志——而误拆则不过是把 一条新闻显示两次。这种不对称——一条新闻看到两次可以挽回，两条被悄悄合并则不能——是这个项目里每一个 dedupe 决定背后的准则。

要么带时区，要么拒收

Item 模型会拒绝 naive datetime，而不是默认它是 UTC。feedparser 返回 naive 的结构体，HN API 返回 带 Z 的 ISO 字符串，arXiv 自带偏移量；默认当作 UTC 是一个数小时的误差，没人会注意到，直到 ranker 按时间新旧排序并把两者混在一起。store 在写入时转成 ISO 字符串，读出时解析回带时区的 datetime，并用一个 +05:30 的值做往返测试——HN adapter 则从整数 created_at_i 取时间戳，时区信息由结构 保证，而不依赖某个后缀。

两个上限，两个名字

fetch_limit 按信息源计，限制摄入；quota 按主题计，限制选取。给它们同一个名字会招来 "到底哪个生效"的 bug，所以有一个测试往 sources.yaml 里塞一个 quota: 键并断言它会 报错。摄入刻意放得宽——arXiv 50、HN 30——因为每条原始载荷都原封不动地存在 raw_json 里，这样当 第三周 ranker 改了之后，可以离线对三周的历史重跑一遍，而不是再等三周才知道改动是否有效。

48 小时窗口，而不是 24

24 小时的创建窗口会永久错过慢热的新闻：一条 30 小时前发布、今天早上才破 100 分的帖子，在两次运行中都不曾 落在窗口内。重新看到昨天的条目没有任何代价，URL 哈希一去重就没了。回看窗口和画像里的 max_age_hours 目前共享 48 这个值，并被注明是两件不同的事，必须保留各自独立变化的自由。

做的过程中发现了什么

每个 phase 的 pull request 都有一个以此为题的小节，因为一个 phase 在它之前的 phase 里发现的 bug，是最值得记录的东西。

fetch 一上线，就有一个测试开始访问网络。phase 0 的一个测试调用了 main(["fetch"])，它悄悄变成了一次对 Algolia 的真实 HTTP 调用——而且通过了，所以没有任何东西标记它。 修复是结构性的，而不是加一句断言：tests/conftest.py 安装了一个 session 级的 socket 守卫，任何测试都 无法选择退出。深挖它的过程中冒出两个细节。loopback 必须豁免，因为在 Windows 上 asyncio 事件循环用一对 127.0.0.1 socket 搭建自己的 self-pipe，一刀切地抛异常会把它本该保护的测试一起干掉。而守卫的异常 派生自 BaseException 而非 Exception：复现这个回归时发现守卫装上后测试依然通过，因为 fetch_all 会捕获所有 Exception 以保证没有哪个信息源能中止运行——于是被拦下的连接 变成了一次记录在案的信息源失败，以及退出码 0。

同一个 catch 还吞掉了 Ctrl-C。追查上面的问题时暴露出 fetch_all 把 KeyboardInterrupt、SystemExit 和 CancelledError 都当成"这个信息源失败了"—— 一次被打断的抓取会被记录成一个死掉的 feed，并在第二天早上的健康页脚里显示为信息源腐坏。现在非 Exception 的 BaseException 会被重新抛出：绝不中止的规则说的是信息源失败，不是操作者退出。

一个只等第一条非 Latin-1 标题出现就会崩溃的 bug。在 Windows 控制台上 sys.stdout 是 cp1252，所以打印一条 CJK 或 emoji 标题会抛出 UnicodeEncodeError，把一个本该在 07:00 无人值守运行 的任务整个打垮。已复现，通过把 stdout 重新配置为 UTF-8 修复，而且值得一提的是 GitHub Action 永远不会复现它—— 所以本地运行是横在它和一次静默失败的早晨之间的唯一屏障。CLAUDE.md 现在对所有文件 I/O 明确要求 encoding="utf-8"，因为 phase 3 的 open(path, "w") 就是同一个 bug 换了个表面。

Algolia 对纯文本帖子会省略 url 字段——而不是发 null。 adapter 本来就会回退到 HN 的条目页，但第一版测试断言的是 is None，对着真实 fixture 就挂了。现在它被 一个参数化测试钉死在全部三种形态上（缺失、null、空字符串），将来从一种变成另一种也不会以崩溃的形式 传到定时任务里。

数字守卫让自己的六个测试挂了，而它是对的。fixture 里那一对是"…at CES 2027"与"…at CES"—— 被标注为重复，但数字不同，所以守卫拒绝了它。错的是标题，不是规则。另外，WAL 模式的 SQLite 在进程被杀后会留下 -wal 和 -shm 伴生文件；直到某次运行被打断之前，它们都不在 .gitignore 里。

开发方法：一个 phase 一个 session

这个项目在写任何代码之前就有两份设计文档——一份构建计划（范围、每个端点都经手动验证的信息源目录、数据模型、 三个递进版本的排序设计、各个 phase），以及一份实施指南，里面写着每个 phase 要用的 prompt 原文。两者都在仓库的 docs/ 下。这套方法承袭自 JHA 的经验：每个 phase 都是一个全新的 Claude Code session， 因此不会有任何漂移，而跨 session 的固定约束由 CLAUDE.md 承载，而不是靠对话记忆。

每个 phase 都走同一个循环。贴上 prompt；prompt 的结尾要求 agent 先给一份简短计划，并在动手之前回答一两个问题 （"说出一种 canonical_url 可能把两个真正不同的 URL 合并成一个的情况"——上文的 source 参数决定正是这样浮现的）。读计划、提出反对、说开始。当它说完成时，我亲自跑验收命令——关掉 wifi 跑测试、第二次 fetch 必须报告 new 0——因为这个项目全是 I/O，而 I/O 正是 agent 的自信最不可靠的地方。然后在一个 全新的 session 里跑一个评审 prompt，它比写代码的那个 session 审得更好，因为它不用为自己的选择辩护。每个 phase 一个 pull request，决定和发现都写进描述里。在 phase 之间，当代码的形态变化足够大时——设计时假设只有一个 adapter，现在有五个——同一套纪律就放大成上文的阶段间 review：先做 snapshot，再跑六轮相互独立的评审，然后 triage，最后一个 session 一个修复主题，每个主题在获准写代码之前先提出自己的计划。

我亲自把关而不委托出去的规则：不经询问不加新依赖（token 集合比值、CLI 和配置加载都是 agent 会伸手去拿 rapidfuzz、typer 或 pydantic-settings 来省二十行代码的地方）；测试不许联网； adapter 保持"笨"；解析不了的抓取器要抛异常而不是返回空列表，因为空列表和"今天没新闻"无法区分，而这恰恰是 健康页脚抓不住的静默腐坏。

分工说得直白一点：计划、约束、phase 边界、验收检查和评审是我的；几乎全部代码是 Claude Code 依据它们写出来的。 上面的"决定"一节，如实记录了 agent 的第一版答案在哪里被改掉、以及为什么。

不足之处

它还产不出摘要。数据库里的五个信息源，外加一份 428 条未渲染条目的纯文本列表，是一个摄入层， 不是一个产品。排序、渲染和定时调度才是决定它究竟能取代 Hacker News、还是沦为又一个我不读的 feed 的部分；计划对这个 风险的回答是：在写任何 LLM 代码之前，先读四个早上的规则排序输出。

近重复检测有一个已知的漏网之鱼。屈折变体是不同的 token，所以一条调换语序的标题—— "Anthropic releases X"与"X released by Anthropic"——只得 0.80，会被当成两条新闻放过。stemming 能修它， 但不在 v1 范围内；这个取舍记录在阈值旁边。

AI 博客镜像逐 feed 来看并不可靠。它六个 feed 里有三个已经陈旧了好几个月，却仍返回 HTTP 200 和格式良好的 XML，而核查过的每一个替代方案都返回 404，所以镜像保留，陈旧度警告是承重的而非装饰性的。 conditional GET 已实现并有测试，但没有持久化：sources 表每个信息源只有一个 etag 列，而合集需要六个，所以每次请求仍然是无条件发出的——刻意不做成半成品，直到真有哪个主机对这个任务限流。

跨信息源重复的优先级是配置顺序，不是一个决定。一篇论文的 arXiv 副本目前指向 Hugging Face 副本，仅仅因为 hf_papers 在 sources.yaml 里排在 arxiv_cs_ai 之前； 把文件按字母排一下序就会悄悄翻转它。phase 3b 欠一个明确的优先级，以及一个把文件重新排序后断言胜出方不变的测试。

review 写明了没有人看过的地方。性能、never-abort 之外的并发、年量级的数据增长、数据库体积和 供应链都不在范围内，而 review 文档把它们列了出来，好让"54 条发现，全部有了决定"在六个月后不会被误当成完整。

从 GitHub Action 提交一个 WAL 模式的 SQLite 文件——phase 5 的计划——需要在 commit 步骤之前先执行 PRAGMA wal_checkpoint(TRUNCATE)，否则提交的文件可能恰好缺少这次运行刚写下的那些事务。已记下留给 phase 5，尚未处理。

一个人的项目，与 agent 协作完成

由曹一明自 2026 年 9 月起设计、主导并评审，作为他本人每天早上使用的工具。用 Claude Code 实现，一个 phase ——或一个 review 主题——一个 session，依据一份书面计划和一份记录固定约束的 CLAUDE.md；分工已在上文说明。
