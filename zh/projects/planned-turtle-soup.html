海龟汤：由 LLM 主持的横向思维推理游戏

一个只能问“是/否”问题的猜谜游戏，由 LLM pipeline（或 agent）主持；玩家每揭开谜底的一部分，LLM 就实时生成场景图像和音效 —— 每一局都独一无二，LLM 的不可预测性从 bug 变成了 feature。

别名： 海龟汤 / Albatross soup / situational puzzle（情境谜题）

核心想法（我自己的话）

  • 玩家通过提问来猜出一个离奇情境背后隐藏的故事；主持人只回答“是 / 否 / 无关”。
  • 随着玩家逐步弄清谜底的每一部分，LLM 实时生成不同的场景图像和音效来营造氛围。
  • 每一局都不一样。LLM 生成固有的随机性 —— 在工程上通常是缺点 —— 在游戏里反而是优势。

为什么有意思

  • 把 LLM 的非确定性变成可重玩性。
  • 规模小到可以作为独立项目交付；又大到足以练完整个多模态技术栈（文本 → 图像 → 音频 → 编排）。
  • 可以直接复用为历史时空穿越模拟器（想法 02）的引擎。

初步的系统大纲

角色 / 组件

  1. Puzzle Author（出题者） —— 生成或挑选一道谜题：表面故事、隐藏真相，以及一份“谜底碎片”列表（玩家必须揭开的 4–8 条事实）。
  2. Host / Judge（主持人 / 裁判） —— 严格以“是 / 否 / 无关”回答玩家的提问，以隐藏真相为依据；绝不泄露。跟踪哪些谜底碎片已被揭开。
  3. Progress Tracker（进度跟踪器） —— 每轮问答之后，把玩家已知的事实与碎片列表做 diff；发出“碎片解锁”事件。
  4. Scene Director（场景导演） —— 每次解锁时，写一条简短的视觉 + 音频 prompt，与已揭示的所有内容保持一致（维护一份持续更新的“scene bible”，让图像在整局中保持连贯）。
  5. Media Generators（媒体生成器） —— 图像模型（场景插画）和音效 / 环境音模型；主持人的声音可能用 TTS。
  6. Game Client（游戏客户端） —— 聊天式 UI；显示当前场景图像、播放音效、展示提问日志和一个“你离答案还有多远”的进度表。

Pipeline 还是 agent

  • 先做成固定的 pipeline：Host → Tracker → Director → 媒体调用。控制流是确定性的，LLM 只在各个盒子内部。
  • 只有在需要时才升级为 agent（例如让 Director 决定是否值得切换场景，或在图像 / 音效 / 什么都不做之间选择）。

需要解决的关键设计问题

  • 谜题来源：手写的经典谜题，还是完全由 LLM 生成的谜题（生成的谜题需要一致性检查，确保故事真的可解）。
  • 延迟预算：图像生成可能需要好几秒 —— 可以投机性地预生成最可能的下一个场景，或在后台生成、就绪后再替换。
  • 一致性：如何让同一角色/地点在多张图像间保持一致（scene bible、复用 seed、参考图像 conditioning）。
  • 裁判可靠性：是/否的回答必须正确；考虑用结构化的隐藏真相表示（事实列表）而不是自由文本，让裁判对照的是数据。
  • 先做多人还是单人？（先做单人；多人是 UI/状态问题，不是 AI 问题。）
  • 每局成本（每次解锁的图像 + 音频调用）。

里程碑

  1. 纯文本 MVP：一道硬编码的谜题，Host 回答提问，Tracker 检测碎片解锁。CLI 即可。
  2. 加入 Scene Director + 解锁时的图像生成；测量延迟和连贯性。
  3. 加入音效 / 环境音；如果效果好，再给主持人加 TTS。
  4. Puzzle Author：LLM 生成谜题，附带可解性检查。
  5. Web 客户端；对局回放 / 分享一条“故事到目前为止”的图像条。

技术备注（初步猜测）

  • Python 编排；Claude/GPT 级别的模型做 Host/Director；图像 API（如 Flux / Imagen / DALL·E 一类）；音频 API（ElevenLabs 音效，或某个开源模型）；FastAPI + 简单的 Web 前端。
  • 处处使用 structured output，让游戏状态是数据而不是散文。
