会议转录 → 实时“外脑”

先基于 MOSS-Transcribe-Diarize 做一个会议转录工具；再一步步把它培育成一个实时助手 —— 听着对话，自动调用 tool 或做深度推理，并把答案快到能在谈话进行中直接使用地交给你 —— 一个外脑。

状态：已记录。 这是大纲，不是实现 —— 记录下来是为了不让想法和待解问题丢失。随着思考深入它会不断修改。创建于 2026-09-12 · 最近更新 2026-09-12。

基础模型： https://github.com/OpenMOSS/MOSS-Transcribe-Diarize（开源的转录 + speaker diarization（说话人分离））

核心想法（我自己的话）

  • 第一步具体且有边界：用这个开源模型做一个会议转录工具（转录稿 + 谁说了什么）。
  • 最终方向尚未确定。一个候选：系统处理对话内容，在谈判或讨论过程中自动调用 tool 或进行深度推理来辅助用户。
  • 触发这个想法的场景（不完美，但抓住了要点）：一个不熟悉智能手机的陌生人向你问路。你想帮忙，但不知道确切路线。这个时刻只有一两秒 —— 没时间掏出手机、打开地图、搜索，再把路线换算成相对于你们俩所站位置的说法。智能眼镜听到问题，自动算出最优路线，让你在一两秒内就能描述出来。这个场景假设你无法自己完成那些手动步骤（受限或没时间）—— 这个约束才是关键所在。
  • 诚实的自我评估：完整愿景很复杂，我缺少部分专业知识，可行性也不确定。所以：先做转录工具，再逐步向实时和更多功能升级。

初步的路线图

阶段 1 —— 离线会议转录工具（真正的第一步）

  • 在本地对录音运行 MOSS-Transcribe-Diarize；输出带 diarization 的转录稿（说话人标签 + 时间戳）。
  • 评估：英文和中文的准确率、中英混杂的会议、硬件要求（需要 GPU？纯 CPU 可行？）、每分钟音频的处理延迟。
  • 加入 LLM 后处理：说话人命名、摘要、行动项、决议。
  • 交付物：一个 CLI 或最小化的 Web 应用，输入一个音频文件，返回一份干净的会议记录。

阶段 2 —— 流式 / 准实时转录

  • 分块或流式推理；测量端到端延迟。
  • 实时转录视图；随会议进行不断更新的滚动摘要。
  • 判断 MOSS 模型对流式的支持是否足够好，还是实时路径需要另一个 ASR 前端（离线高质量那一遍继续用 MOSS）。

阶段 3 —— 对话理解 + tool 触发

  • 对实时转录做意图检测：“这里是否有一个用户无法立刻回答的问题？”（路线、某个事实、某个数字、某个日期、一句翻译）。
  • Tool router：把检测到的需求映射到 tool（地图/路线规划、搜索、计算器、日历、翻译）。
  • 输出必须可以说出口：一句用户能直接念出来的话，而不是一页结果。对于路线：相对于当前位置和朝向。
  • 延迟目标：问题说完后约 1–2 秒内给出答案。这是塑造一切的硬约束（用小而快的模型做检测、预热 tool、投机执行）。

阶段 4 —— 可穿戴 / 眼镜形态的交付（遥远的未来）

  • 智能眼镜或耳机形态；音频输入，文本/音频输出。
  • 隐私：在设备端运行，或至少由用户控制；录制他人需征得同意。

关键问题

  • 能证明这个闭环（听到 → 判断 → tool → 可说出口的答案）成立的最小可行“外脑”demo 是什么，哪怕一开始延迟有 5 秒？
  • 哪些 tool 值得先做？（路线是旗舰示例；翻译大概是最容易拿下的实际收益。）
  • 如何避免助手在不需要的时候打断或抢答（按键提问 vs. 常驻建议）。

技术备注

  • Python；按仓库说明运行 MOSS 模型；LLM 做后处理和意图识别；之后实时路径用一个快速的小模型。
  • 个人硬件：确认我的家用集群 / 笔记本 GPU 能否跑动这个模型。
