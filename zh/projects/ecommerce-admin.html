用 Go 和 React 构建的网店后台

每一家网店都有第二个应用，没有顾客会在里面购物：员工在那里管理用户、角色、商品目录和 源源不断的订单。这就是那个应用，分成两个仓库构建——一个基于 Fiber 和 GORM 的 Go REST API，以及一个 TypeScript 编写的 React 仪表盘——会话为存放在 HTTP-only Cookie 中的 JWT，访问控制基于角色并细化到权限级别。项目起源于一门课程。属于我自己的部分是：把每个库 移植到今年的版本、为每一个文件撰写文档，以及在本页如实梳理这份代码做得好的地方与不足之处。

让一个请求穿过 middleware

go-admin/middlewares 中的两个 middleware 和 util/jwt.go 中的 JWT 校验，用 JavaScript 逐行重新实现。选择一个角色、一种 Cookie 状态和一个请求；下面的追踪 就是 Go 代码实际执行的过程。

GET /api/users?page=1

    —

    两道串联的关卡。第一道只问一件事：Cookie 里的 token 是否由本服务器签发且尚未过期；它从不 访问数据库。第二道加载用户的角色及其权限，并套用一条规则：GET 请求只要有 view_<page> 或 edit_<page> 之一即可通过，其他方法 都需要 edit_<page>。试试用 viewer 角色发起 DELETE /api/users/7。

    两个仓库各做什么

    go-admin 是 API：二十个 Go 文件，二十八条路由，基于 Fiber v3，用 GORM 连接 MySQL。两条路由是 公开的——注册与登录。routes.go 中位于 app.Use(middlewares.IsAuthenticated) 之后的一切都需要 Cookie：当前用户的 资料与密码、用户/角色/商品的完整 CRUD、权限列表、一个上传后直接作为静态内容回传的图片 接口、带明细项的分页订单、CSV 导出，以及一条为仪表盘图表供数的聚合查询。

    react-admin 是仪表盘：React 19 与 TypeScript 编写的十四条路由。一个 Wrapper 组件守卫 每一个页面——挂载时调用 GET /api/user，把结果放进 Redux store，若 Cookie 缺失或失效则重定向到 /login。围绕它的是带分页的列表页、创建与编辑表单 （角色表单把每个权限渲染成一个复选框）、一个提交 multipart 表单数据并把返回 URL 填入 商品表单的图片上传组件、一张行可展开显示明细项的订单表，以及一张由 /api/chart 接口供数、用 c3.js 绘制的每日销售额柱状图。

    公开 POST/api/register · /api/login 会话 — 位于 app.Use(IsAuthenticated) 之后 GET/api/user POST/api/logout PUT/api/users/info · /api/users/password 用户、角色、商品 — CRUD GET/api/users?page=n · /api/users/:id · /api/roles · /api/roles/:id · /api/products?page=n · /api/products/:id · /api/permissions POST/api/users · /api/roles · /api/products · /api/permissions PUT/api/users/:id · /api/roles/:id · /api/products/:id DELETE/api/users/:id · /api/roles/:id · /api/products/:id 文件、订单、统计 POST/api/upload (multipart) · /api/export (CSV 下载) GET/api/uploads/* (静态) · /api/orders?page=n · /api/chart

    会话：一枚浏览器读不到的签名 token

    登录时用 bcrypt 校验密码——cost 因子为 14，单次哈希耗时约一秒，这正是目的所在——然后 签发一个 JWT，其声明只有两项：作为 iss 的用户 id，以及 24 小时的 exp。token 通过标记为 HTTPOnly 的 Cookie 返回，因此页面 JavaScript 永远读不到它，被注入的脚本也无物可窃。之后浏览器会自动把它附加到每一个 请求上；React 一侧只需设置 axios.defaults.withCredentials = true，API 一侧则需在 CORS 中为一个指定来源应答 AllowCredentials: true。 

    // controllers/authController.go — bcrypt.CompareHashAndPassword 成功之后
token, err := util.GenerateJWT(strconv.Itoa(int(user.Id)))

cookie := fiber.Cookie{
    Name:     "jwt",
    Value:    token,
    Expires:  time.Now().Add(time.Hour * 24),
    HTTPOnly: true,
}
c.Cookie(&cookie)

// util/jwt.go — middleware 在每个请求上对它做的事
func ParseJWT(cookie string) (string, error) {
    token, err := jwt.ParseWithClaims(cookie, &jwt.StandardClaims{},
        func(token *jwt.Token) (interface{}, error) { return []byte(SecretKey), nil })
    if err != nil || !token.Valid {
        return "", err
    }
    return token.Claims.(*jwt.StandardClaims).Issuer, nil   // 用户 id
}

    登出就是同一个 Cookie，值为空、过期时间设为一小时之前。服务器从不存储会话，这使 API 成为无状态的——也使得在 24 小时到期之前无法撤销 token。这个取舍是设计上的有意为之， 但值得心中有数。

    角色、权限与关联表

    一个用户有一个角色；一个角色通过 role_permissions 表拥有多个权限，这张表 由 GORM 根据一个 struct 标签自动建立。权限只是名字，而 view_users / edit_products 这一命名约定正是 middleware 匹配的依据——这意味着管理员可以在 仪表盘里为新资源创建权限，无需改动代码。 

    type Role struct {
    Id          uint         `json:"id"`
    Name        string       `json:"name"`
    Permissions []Permission `json:"permissions" gorm:"many2many:role_permissions"`
}

// middlewares/permissionMiddleware.go
if c.Method() == "GET" {
    for _, permission := range role.Permissions {
        if permission.Name == "view_"+page || permission.Name == "edit_"+page {
            return nil
        }
    }
} else {
    for _, permission := range role.Permissions {
        if permission.Name == "edit_"+page {
            return nil
        }
    }
}
c.Status(fiber.StatusUnauthorized)
return errors.New("unauthorized")

    真正生效的位置。权限检查是由控制器调用的一个函数，而不是路由器上的 middleware——而在这个仓库里，只有五个用户 handler 调用了它。角色、商品和订单仅由 Cookie 保护。上面的模拟器默认采用这一真实接线方式；勾选复选框则展示预期设计的行为。扩展它只需 在每个 handler 顶部加一行调用，这也是本页底部清单上的第一项。

    一个分页器服务所有表

    用户、商品和订单都以 ?page=n 列出，并以相同的结构应答。与其把偏移量运算 复制三份，各模型共享一个接口——任何能计数自身、并能取出自身一段切片的东西都可以分页—— 订单模型则用它的 Take 完成本来会在控制器里重复的工作：用一条查询预加载 明细项，并在返回途中计算每个订单的总额和显示名。 

    type Entity interface {
    Count(db *gorm.DB) int64
    Take(db *gorm.DB, limit int, offset int) interface{}
}

func Paginate(db *gorm.DB, entity Entity, page int) fiber.Map {
    limit := 5
    offset := (page - 1) * limit
    data := entity.Take(db, limit, offset)
    total := entity.Count(db)
    return fiber.Map{
        "data": data,
        "meta": fiber.Map{"total": total, "page": page,
                          "last_page": math.Ceil(float64(total) / float64(limit))},
    }
}

// models/order.go
func (order *Order) Take(db *gorm.DB, limit int, offset int) interface{} {
    var orders []Order
    db.Preload("OrderItems").Offset(offset).Limit(limit).Find(&orders)   // 一条查询，而非 N+1
    for i := range orders {
        var total float32 = 0
        for _, item := range orders[i].OrderItems {
            total += item.Price * float32(item.Quantity)
        }
        orders[i].Name  = orders[i].FirstName + " " + orders[i].LastName
        orders[i].Total = total
    }
    return orders
}

    属于我的部分：移植到当前版本
    
      
    
        技术栈里的每一个库自课程录制以来都发布过大版本更新。我基于 2025 年末的最新版本构建——
        Go 1.25、Fiber v3（release candidate 2）、GORM 1.31、React 19、React Router 7、
        Redux 5 与 react-redux 9——这意味着课程里教的代码有相当一部分无法编译或无法运行，我必须
        阅读各个库的迁移说明才能弄清原因。
      
    
      
    
        Go 一侧，Fiber v3 把 handler 的签名从指针改成了接口（func(c fiber.Ctx) error），
        用绑定 API（c.Bind().Body(&data)）取代了 c.BodyParser，把
        静态文件服务从 app 中移到了 middleware（static.New("./uploads")），并把 CORS
        配置改为用函数指定允许的来源。React 一侧，Router 7 没有 Redirect、没有
        Switch，也没有 props.match：每一个从 URL 读取 id 的页面都改成了
        useParams 钩子，每一次保存后的重定向都改成了渲染
        <Navigate>。React 19 更严格的类型迫使 API 响应经过显式类型转换，模型
        也改写为 TypeScript 的类和接口。这些工作没有一项光鲜；但正是它们把一份教程变成了
        真正能跑起来的东西。
      
    
      
    
        另一件属于我的事是文档。每个 Go 文件都有头部注释，每个 handler 都说明了它做什么、返回
        什么；React 组件也一样。两份 README 都是从零写起——功能、前置条件、安装、API 接口、
        数据模型——让克隆任一仓库的人不用看课程也能把它跑起来。
      
    
    
    
  
    

    



    
  
    
    
    
      
    上线之前，我会改什么
    
      
    
        这是一个学习性项目，有些地方读起来也确实如此。逐文件写完文档之后，下面是我接下来会
        按顺序着手的清单。
      
    
      
    
        
    
          源码中的密钥。JWT 签名密钥是 util/jwt.go 中的一个常量，
          数据库 DSN 是 database/connect.go 中的一个字面量。两者都应放进环境变量，
          而且鉴于仓库历史记录的存在，密钥无论如何都应当轮换。
        
    
        
    
          授权覆盖范围。如上所示，只有用户 handler 调用了 IsAuthorized。
          角色、商品和订单也应当调用，并且检查失败时应返回 403 Forbidden 而不是
          401——请求已经通过了认证，只是不被允许而已。
        
    
        
    
          上传。c.SaveFile(file, "./uploads/"+file.Filename)
          信任了客户端提供的文件名。它需要生成的文件名、扩展名白名单和大小上限。
        
    
        
    
          用 float32 表示金额。价格和总额都是浮点数，CSV 导出还把它们截断成
          整数。应改为以整数列存储分、或使用 decimal 类型，并对导出做格式化。
        
    
        
    
          其他小问题。页大小是一个字面量 5；CSV 导出在流式输出前
          先写到磁盘上的固定路径；而且没有测试。针对内存 SQLite 写几个 handler 测试，本可以在
          本页之前就抓住那个截断 bug。
