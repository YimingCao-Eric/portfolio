方法 · 我如何与 AI agent 一起构建软件

严谨要分阶段：我如何与两个 AI agent 一起构建软件

我用两个 AI agent 和一套成文的方法来做自己的项目。一个 agent 和我一起规划，并撰写所有文档；另一个编写每一行代码； 由我做决定、使用产品并提交代码。这套方法决定严谨用在哪里 —— 代码还是用完即弃的原型时，几乎不设约束；代码要长期保留时， 规则全部生效 —— 而在两者之间，还有一个阶段：先每天使用产品，再在代码冻结的状态下对它进行测量。

一份持续更新的文档。2026 年 9 月 18 日初稿；9 月 25 日根据在 My Daily News 上运行一周的经验重写； 9 月 27 日合并为一份文档；9 月 28 日再次修订。每条规则都写明了理由，因为理由被遗忘的规则，迟早会被重新争论一遍。 最近更新 2026-10-04。

阶段 0 · 想法

不算一个正式阶段。把一个还不成熟的想法写下来 —— 一段话、一条笔记，而不是一份文档 —— 免得它丢失。

参与者
只有我。
产出
想法文件夹里的一条笔记。
规则
没有：没有结构，也没有退出标准。
如何结束
我决定开始，而开始就意味着进入阶段 1。
My Daily News
一条笔记，最初是“一个覆盖我所关注一切的个性化 Hacker News”，以 AI 作为第一个领域。

阶段 1 · 假设

在和规划一方的对话中，想法被打磨成一个只存在于纸面上的产品：它做什么、不做什么、它对世界有哪些假设，以及什么能证明每个假设是错的。这个阶段什么都不构建。一个用 demo 验证比继续思考更省事的问题，会被标记给阶段 2，而不是在这里争论。

参与者
我和规划一方。没有 coding agent，没有代码。
产出
PRODUCT.md —— 首次运行的那句话（demo 第一次运行时必须展示什么，我才会说“就是这个”）、产品的形态、每个假设以及 demo 必须通不过才能推翻它的检验、可预见的问题、不做的范围；最后永远是 Pending 和 Open 两节。PLAN.md —— 后续每个阶段如何推进，让阶段 2 从计划出发，而不是凭惯性开始。
规则
没有可推翻检验的假设只是前提，要作为前提单独列出。
如何结束
一个五项检验，由规划一方执行，而不只是由我确认：每个假设都有 demo 能执行的检验；每个可预见的问题都有答案，或被标记给阶段 2；首次运行的那句话仅凭形态一节就能推出；最后一遍完整审阅没有增加任何 demo 能更快解决的内容；计划写明了阶段 2 的第一件事是决定运行环境。我接受的是记录检验结果的那段话 —— 是那段话，而不是这个阶段。
My Daily News
9 月 18 日结束，产品写在纸面上：首次运行的那句话，以及每个假设和能推翻它的结果。

阶段 2 · 原型

这个阶段从决定生产环境开始 —— 技术栈、运行时、代码在哪里运行 —— 只看它是否适合这个项目，而不看谁更熟悉它。然后快速构建一个原型，用事实检验产品文档；每次修正产品，都在同一轮中同步修正文档。原型要实现并测试功能；只有需要时间积累、无人值守运行或尚不存在的数据的部分，才推迟到下一阶段，并写明理由。

参与者
三方，从第一个 session 开始。
产出
一个放在 lab/ 里、仅作参考的可运行原型；随时修正的 PRODUCT.md；一份由规划一方撰写的日志。
规则
放宽的：review 的是行为，不是代码；只有涉及产品行为的分岔才拿给我决定 —— 命名、库和布局由离得最近的一方挑选并记录。不放宽的，即控制围栏：原型代码永远不会成为正式代码库；每个关于数据的结论都要先测量再陈述；测试永远不碰产品的真实数据，由一道在测试运行前对数据做哈希的“绊线”强制执行；任何破坏性操作之前先做快照；仓库里不放任何密钥。
如何结束
每个假设都已测量，或已推迟到阶段 2.5 并写明理由。日志关闭。
My Daily News
计划里写的是“少量几个 session”，实际跑了大约三十个 —— 这就是 session 预算被从方法中删除的原因。

阶段 2.5 · 先使用，再测量

有些假设需要几天的使用才能检验，而离开阶段 2 的原型也从来不会完全符合最初的设想。阶段 1：每天早上使用，当天修复使用中暴露的问题。阶段 2：冻结代码并测量，每项测量都对照一个在数据出现之前就定好的阈值。下面的图 B 会逐日运行这些规则。

参与者
三方；session 按天命名。
产出
一份每日日志，每个日期一节，新的一天开始后即冻结；各项测量的结论；然后是 SPEC.md，依据原型的实际表现撰写，每条需求都能追溯到观察到的事实。
规则
当天发现的问题当天解决，否则标记为“延后”并写明理由。阶段 2 从这样一天之后开始：使用中没有需要改代码的发现，之后也没有代码合入。任何代码改动都会让计数重来。每个测量日被采纳之前，都要检查冻结是否成立。
如何结束
报告各项结论 —— 得不出结论的测量也是一个结果，连同原因一起写明 —— 规格说明被接受，边界问题有了书面回答。
My Daily News
阶段 1 从 9 月 24 日开始 —— 使用了四个早晨，第一个早晨就有十个发现。阶段 2 从 9 月 28 日开始 —— 代码冻结，五个早晨对照数据出现前写下的标准进行测量。已有一个假设低于标准，这个“未通过”保持不变。

阶段 3 · 构建

从一棵空的代码树重新开始，采用确定性的架构，依据已稳定的规格说明编写。原型只作参考，永远不会被直接转为正式代码。原型是在 agent 完全掌控下 vibe-coding 出来的；这里则由人来 review 和修改代码。

参与者
三方，代码由人 review。
产出
产品的代码库。
规则
原型阶段暂停的严格规则在这里恢复：每个 diff 只做一个决定；分岔在写代码之前提出；每条 prompt 都逐字记录在日志里。
如何结束
和每个边界一样，以书面回答边界问题结束。

阶段 4 · 部署

产品正式发布，并在真实环境中运行。

上线时
产品的代码树会被清理干净：lab/ 和 docs/ 在同一个 commit 中移出，这样克隆下来的只有产品本身。历史记录仍然保留它们 —— 目的是让产品干净，而不是把过程藏起来。
规则
那些始终有效的规则：仓库里不放密钥，在规定的节点备份，结束时回答边界问题。

为什么需要一套方法

My Daily News 是我第三次尝试同一个想法，而前两次恰好从相反的方向失败。第一次按计划逐步推进，由 coding agent 实现每一步。 它产出了可运行的代码，但随着代码增长，我的 review 变得流于表面，我失去了对项目走向的掌控。第二次则对一切都套用严格的规则 —— 先探查再构建，每个设计分岔都用真实数据检验，每次改动只做一个决定，保留完整的书面记录。掌控从未丢失，但三天里连一个 demo 都没做出来：规则本身是对的，却花在了用完即弃的代码上。事后我写下的只有一句话。

“严谨要分阶段。”

这套方法就是把这句话展开成细节。它把做决定的人、负责规划的 agent 和负责写代码的 agent 分开；把说明产品“是什么”的文档， 和记录它“如何走到这一步”的文档分开；并且逐个阶段写明，哪些规则放宽，哪些规则永不放宽。

三个参与者，以及各自负责的东西

我

决定、使用、提交

由我决定产品是什么、使用它、评判每一份报告，并完成每一次提交。

确定性的工作 —— 一次抓取、一条输出固定且可预知的命令 —— 默认由我来做，因为让 agent 做既耗 token，又可能产生幻觉。只有当拆分出来会打断一项任务的连续性时，才交给 coding agent。

规划一方

Cowork 中的 Claude

和我一起思考，并负责所有文档：产品文档、计划、日志、阶段边界的总结段落、给 coding agent 的 prompt，以及仓库里的 CLAUDE.md。

它可以读取任何文件，用自己的脚本测量数据，移动和备份文件。它从不运行、修改或验证产品的代码。

Coding agent

Claude Code

负责代码：编写、运行、测试，然后汇报。它不提交代码，也不写规划文档。

它在文档中发现的问题会被报告出来，由我决定，再由规划一方修改。它在阶段 2 之前不参与。

界线划在产品的代码上，而不是文件系统上，理由正是整个安排的意义所在：在 agent 的工作循环之外对代码做的改动不会被记录， 而没有记录的改动就是一个黑箱。因为规划一方从不碰代码，coding agent 也从不写文档，所以对产品的每一次改动， 都要经过一份书面 prompt 和一份书面报告。

三类文档

类别用途文件
产品定义产品 —— 它是什么PRODUCT.md；阶段 2.5 结束后还有 SPEC.md
计划每个阶段如何推进：方法、操作手册、各项测量及其阈值PLAN.md
日志发生了什么、决定了什么、哪里出了错每个阶段一份；阶段 2.5 另有一份每日日志

这样划分是为了消除一种含糊：一份产品文档如果同时记录它是如何得出这些内容的，就不再能当作产品文档来读。所以 PRODUCT.md 只陈述产品是什么，不留下任何已被取代的内容，并且永远以同样顺序的两节结尾 —— Pending，所有待办事项及其等待的阶段；然后是 Open，等待决定的问题。 每一次带日期的推导、每一个算过成本的选项、每一条被推翻的建议，都放在日志里。

从阶段 1 开始，所有文档都放在仓库的 docs/ 里。原型代码放在 lab/ 里并纳入版本控制，让每个 session 都是一个 diff；它的数据则不进 git，因为里面有 session cookie、token 和个人记录。CLAUDE.md 由规划一方撰写，coding agent 在每个 session 开始时读取。备份放在所有仓库之外，每份都附哈希清单，这样仓库里的一条错误命令碰不到它们。

一个 session，从 prompt 到提交

  1. 规划一方在使用的那一刻撰写 prompt，从不提前写好，作为一整块可复制的内容交给我，由我粘贴。
  2. Coding agent 开始工作，并按固定的五个部分汇报。
  3. 规划一方对照报告提到的文件核查报告，验证每一个打算复用的数字，在同一轮中更新 PRODUCT.md，并把这个 session 写进日志 —— 包括它自己哪里做错了。
  4. 由我提交。

每条 prompt 都写明要读取的文档的真实路径，写明不要提交，写明永远不要读取、打印或回显 .env，要求在任何破坏性操作之前先做快照，并在最后要求报告所有没被问到却发现了的东西。改变某个键、路径或字段推导方式的 prompt，要列出它的每一个读取方；删除某样东西的 prompt，要记录下什么情况发生时这次删除会变成错误。

每份报告都有同样的五个部分：运行了什么，快照在哪里；结果是什么，附上数字 —— 永远不能只写“测试通过”； prompt 没有规定之处所做的选择；所有没被问到却发现了的东西，以及 prompt 里被证明有误的地方；最后一行确认没有提交任何东西，也没有改动任何文档。

阶段 2.5：先使用，再测量

有些假设无法立即检验 —— 它们需要几天的使用、时间的推移，或者逐渐积累的数据。而离开阶段 2 的原型也从来不会完全符合设想： 它第一次被真正使用时就会暴露问题。所以在原型和构建之间，有一个独立的阶段，分为两部分，而这个顺序的理由只有一句话：

“冻结，是在声称这个东西已经完成到足以测量的程度。”

阶段 1 —— 每日迭代。每天早上使用原型，并在当天根据使用中暴露的问题修改它。当天发现的问题当天解决； 没有解决的，日志里写“延后”并给出理由，因为延后的问题是一个决定，而不是疏忽，它必须看起来就像一个决定。新的一天开始后， 前一天的那一节即被冻结。这里什么都不测量：修改页面会往产品自己的使用日志里写入真实事件，和读者的操作无从区分。 代码还在变动时，仪器记录的是作者。

进入阶段 2。一天达标的条件是：使用产品没有产生需要修改代码的发现，并且之后没有代码合入。这里的“发现”指的是 使用中的发现：测试或 agent 报告中发现的缺陷不会让这一天不达标，因为被测试抓到的缺陷，恰恰证明流程在起作用。

阶段 2 —— 稳定期。任何会改变受测代码的事情都不会发生。每项测量都对照一个在数据出现之前就定好的阈值 —— 看到数字之后才选定的规则只是描述，不是阈值 —— 得不出结论的测量也是一个结果，连同原因一起报告。任何代码改动都会让流程回到阶段 1， 计数从头开始。重新开始的成本被刻意设计得很低，所以直接重来，而不是争论。每个测量日被采纳之前，都要检查冻结是否成立： 与阶段边界上打了 tag 的 commit 做 diff，git 管不到的部分则用哈希清单核对。

有一条规则是在运行中加上的。那天晚上，阶段 1 的最后几项修复已经就绪，选择是：合入修复，再用一天时间使用之后才冻结； 或者合入修复，第二天早上就开始测量。我的回答现在写进了方法里：

“如果需要修改，稳定期顺延一天就是了。”

所以，最后一次改动之后的第一次阅读，可以临时算作测量的第 1 个早晨：只有当这次使用没有发现需要修复的问题、之后也没有代码合入时， 它才成立。重新计数的规则完全保留，改动后的产品在任何测量日成立之前仍然会被阅读一次。产品稳定之后，才依据原型的实际表现撰写 SPEC.md —— 不会更早。

每个方块是一天。点击可以更改那一天发生了什么；其余的交给上面的规则。预设重放的是 My Daily News 从第一个使用早晨开始的过程。

日期
需要测量的早晨
已读 · 无需改动 已读 · 有发现 → 当晚修复 已读 · 仍有代码合入 未阅读

    在每个阶段都有效的规则

    规划一方的每次回复都分三部分

    边界检查 —— 当前阶段、子阶段，以及哪些退出标准已满足、哪些没有。改了什么 —— 先按文件，再按小节。你的下一步 —— 只包括只存在于我脑中或只能由我动手的事；规划一方自己能读到或能运行的，不会交给我。

    只有重要的分岔才提出来

    只有在各个选项已经用真实数据跑过、并且结果确实不同之后才提出；结果相同，就由规划一方挑选、记录测量结果，然后继续。分岔要以带成本的选项加上一个建议的形式出现 —— 永远不能是一个已经替我选好答案的问题。

    决策规则先于数字

    任何要拿来对照某个数字的规则，都必须在这个数字出现之前定下来并写下来。

    在规定的节点备份，从不临时起意

    在任何删除、迁移或修复数据的 session 之前；在任何文档重组之前；在每个阶段或子阶段的边界上 —— 每份都附哈希清单。因为碰巧想到才做的备份，不是方法可以依赖的备份。

    引用指向稳定的东西

    从文档外部引用时，指向做出改动的那个 session，或按名字指向一条规则 —— 永远不用行号或小节编号。位置会变，而一个指错了规则的指针，比什么都没指向更糟。

    每个边界只问一个问题

    “是产品错了，还是这个阶段的做法错了？”—— 在每个阶段或子阶段的边界上书面回答。它取代了 session 预算，而这正是预算本来要起的作用。

    停下来也是一个结果

    任何阶段都可以以“停止”结束。假设一再不成立的产品，以一份总结收尾：有记录的负面结果是正当的交付物，停下来只需要写下理由。

    教训有一个收件箱

    每个项目都有一份教训文件，学到东西的当天就写进去，并附上它建议的方法改动。在每个阶段结束时，我对每一条做决定；被批准的会成为这里的一条规则。一条教训的文字同一时间只存在于一处 —— 放在两处的教训会逐渐走样。

    仓库里没有密钥

    凭证只放在 .env 里，无论 agent 还是规划一方，都不读取、打印、回显或提交它。过程中的其他一切都可以公开。

    实践：My Daily News

    这套方法是根据在 My Daily News 上运行一周的经验重写的，而这个项目的文档是公开的，所以上面的每条规则，都可以对照它所来自的记录去核实。

    原型阶段计划的是少量几个 session，实际跑了大约三十个；当时没人在计数，于是预算机制被移出了方法。阶段 2.5 于 9 月 24 日开始， 第一个真实使用的早晨就有十个发现 —— 正是这个早晨说明了，冻结之前必须先有真实的使用。“绊线”在第一天就抓到了一个测试： 这个测试遗留的后台任务往真实日志里写入了两行。测量的早晨从 9 月 28 日开始，运行在冻结的版本上，每个早晨被采纳之前， 都要对照一份 53 个文件的哈希清单重新核对。

    规则在不方便的时候也守住了。模型的分类与我自己标注的一致率是 83.1%，而事先定下的标准是 85%；合并两个类别本可以让它通过， 但这个方案被否决了，因为为了通过某个数字而做的改动，出发点就错了，所以“未通过”保持不变。第一个测量早晨只是晚上大约半分钟的浏览， 它该不该算数被作为一个分岔提了出来：三个选项，各附成本，外加一个建议 —— 重新计数。我选择保留这个早晨，因为它满足所有在数据出现之前写下的规则， 而因为数字看起来奇怪就丢掉一个早晨，就是在看到数字之后才选规则。那些算过成本的选项随后从规格说明移到了日志里，因为已经决定的选项不留在规格说明中。

    • PRODUCT.md ↗产品是什么，最后是 Pending 和 Open 两节。
    • PLAN.md ↗每个阶段如何推进，包括阶段 2.5 的各项测量及其阈值。
    • PHASE1-LOG.md ↗假设阶段已关闭的记录。
    • PHASE2-LOG.md ↗原型阶段已关闭的记录，逐个 session 记录。
    • DAILY-LOG.md ↗阶段 2.5，每天一节，下一天开始时即冻结。
    • lab/CLAUDE.md ↗Coding agent 在每个 session 开始时读取的内容。
    • lab/ ↗原型本身 —— 仅作参考，永远不会被直接转为正式代码。

    方法如何演变

    这套方法是一份文档，它的变化方式和产品一样：依据证据，并写明理由。运行中遇到的每一处含糊，都交给我来定夺， 我给出了原话的地方就记下原话，每一项定夺都和它产生的规则记录在一起 ——“删掉预算机制。”“临时起意的备份不算有效备份。” “阶段 2.5 位于阶段 2 和阶段 3 之间；严格来说，SPEC.md 是在产品稳定之后才写的。”

    不足之处

    它来自一个产品的一周。这些规则是根据 My Daily News 上发生的事情重写的。只运行过一次的规则只有一个数据点， 每一个新项目在使用这套方法的同时，也是在检验它。

    它要花日历上的时间。阶段 2 需要真实的使用早晨。错过一个早晨要搭上一天，出现一个发现就要重新计数 —— 这是一次有意义的测量的代价，用天数来支付。

    记录只由一个人核查。规划一方撰写每一份日志，并把自己的错误和 coding agent 的错误记在一起，但每一次 review 最终都落在我身上。 这套方法让黑箱更不容易出现，却不能代替第二位 reviewer。

    它靠一份文档来承载。这套方法本打算做成一个 skill，让一个全新的规划 session 从第一次回复起，就表现得像规划一方实践一周之后那样。 这项工作目前暂停；现在，这套方法存在于它的文档里，也存在于这个页面上。
