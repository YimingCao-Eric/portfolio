A store's back office, in Go and React

Every online shop has a second application nobody shops in: the one where staff manage users, roles, the product catalogue and the orders that come in. This is that application, built as two repositories — a Go REST API on Fiber and GORM, and a React dashboard in TypeScript — with JWT sessions in an HTTP-only cookie and role-based access control down to the permission. It started from a course. What's mine is the port to this year's versions of every library, the documentation of every file, and the accounting on this page of what the code does well and where it's thin.

Send a request through the middleware

The two middlewares from go-admin/middlewares and the JWT check from util/jwt.go, re-implemented line for line in JavaScript. Pick a role, a cookie state and a request; the trace is what the Go does.

GET /api/users?page=1

    —

    Two gates in series. The first only asks whether the cookie holds a token this server signed and hasn't expired; it never touches the database. The second loads the user's role and its permissions and applies one rule: a GET passes on either view_<page> or edit_<page>, anything else needs edit_<page>. Try the viewer role with DELETE /api/users/7.

    What the two repositories do

    go-admin is the API: twenty-eight routes across twenty Go files, on Fiber v3 with GORM over MySQL. Two routes are public — register and login. Everything after app.Use(middlewares.IsAuthenticated) in routes.go needs the cookie: the current user's profile and password, full CRUD for users, roles and products, a permission list, an image upload that's served straight back as static content, paginated orders with their line items, a CSV export, and one aggregate query that feeds the dashboard chart.

    react-admin is the dashboard: fourteen routes in React 19 and TypeScript. A Wrapper component guards every page — it calls GET /api/user on mount, puts the result in a Redux store, and redirects to /login if the cookie is missing or stale. Around that sit the list pages with pagination, the create and edit forms (the role form renders every permission as a checkbox), an image-upload component that posts multipart form data and drops the returned URL into the product form, an orders table whose rows expand to show line items, and a daily-sales bar chart drawn with c3.js from the /api/chart endpoint.

    Sessions: a signed token the browser can't read

    Login checks the password with bcrypt — cost factor 14, so a single hash takes on the order of a second, which is the point — then signs a JWT whose only claims are the user's id as iss and a 24-hour exp. The token goes back in a cookie marked HTTPOnly, so page JavaScript can never read it and an injected script has nothing to steal. The browser attaches it to every later request on its own; the React side only has to set axios.defaults.withCredentials = true and the API has to answer CORS with AllowCredentials: true for one named origin. 

    // controllers/authController.go — after bcrypt.CompareHashAndPassword succeeds
token, err := util.GenerateJWT(strconv.Itoa(int(user.Id)))

cookie := fiber.Cookie{
    Name:     "jwt",
    Value:    token,
    Expires:  time.Now().Add(time.Hour * 24),
    HTTPOnly: true,
}
c.Cookie(&cookie)

// util/jwt.go — what the middleware does with it on every request
func ParseJWT(cookie string) (string, error) {
    token, err := jwt.ParseWithClaims(cookie, &jwt.StandardClaims{},
        func(token *jwt.Token) (interface{}, error) { return []byte(SecretKey), nil })
    if err != nil || !token.Valid {
        return "", err
    }
    return token.Claims.(*jwt.StandardClaims).Issuer, nil   // the user id
}

    Logout is the same cookie with an empty value and an expiry an hour in the past. The server never stores sessions, which is what makes the API stateless — and also what makes it impossible to revoke a token before its 24 hours run out. That trade is deliberate in the design and worth knowing about.

    Roles, permissions, and the join table

    A user has one role; a role has many permissions through a role_permissions table that GORM builds from a single struct tag. Permissions are just names, and the convention view_users / edit_products is what the middleware matches against — which means an administrator can invent a new resource's permissions from the dashboard without a code change. 

    type Role struct {
    Id          uint         `json:"id"`
    Name        string       `json:"name"`
    Permissions []Permission `json:"permissions" gorm:"many2many:role_permissions"`
}

// middlewares/permissionMiddleware.go
if c.Method() == "GET" {
    for _, permission := range role.Permissions {
        if permission.Name == "view_"+page || permission.Name == "edit_"+page {
            return nil
        }
    }
} else {
    for _, permission := range role.Permissions {
        if permission.Name == "edit_"+page {
            return nil
        }
    }
}
c.Status(fiber.StatusUnauthorized)
return errors.New("unauthorized")

    Where it's actually enforced. The permission check is a function the controllers call, not a middleware on the router — and in this repository only the five user handlers call it. Roles, products and orders are protected by the cookie alone. The simulator above defaults to that real wiring; the checkbox shows what the intended design does. Extending it is a one-line call at the top of each handler, and it's first on the list at the bottom of this page.

    One paginator for every table

    Users, products and orders all list with ?page=n and answer with the same shape. Rather than three copies of the offset arithmetic, the models share an interface — anything that can count itself and take a slice of itself can be paginated — and the order model uses its Take to do the work that would otherwise be repeated in a controller: preload the line items in one query, and compute each order's total and display name on the way out. 

    type Entity interface {
    Count(db *gorm.DB) int64
    Take(db *gorm.DB, limit int, offset int) interface{}
}

func Paginate(db *gorm.DB, entity Entity, page int) fiber.Map {
    limit := 5
    offset := (page - 1) * limit
    data := entity.Take(db, limit, offset)
    total := entity.Count(db)
    return fiber.Map{
        "data": data,
        "meta": fiber.Map{"total": total, "page": page,
                          "last_page": math.Ceil(float64(total) / float64(limit))},
    }
}

// models/order.go
func (order *Order) Take(db *gorm.DB, limit int, offset int) interface{} {
    var orders []Order
    db.Preload("OrderItems").Offset(offset).Limit(limit).Find(&orders)   // one query, not N+1
    for i := range orders {
        var total float32 = 0
        for _, item := range orders[i].OrderItems {
            total += item.Price * float32(item.Quantity)
        }
        orders[i].Name  = orders[i].FirstName + " " + orders[i].LastName
        orders[i].Total = total
    }
    return orders
}

    What's mine: the port to current versions
    
      
    
        Every library in the stack has had a major release since the course was made. I built
        on what was current in late 2025 — Go 1.25, Fiber v3 (release candidate 2), GORM 1.31,
        React 19, React Router 7, Redux 5 with react-redux 9 — which meant that a fair share of
        the code as taught didn't compile or didn't run, and I had to read the libraries'
        migration notes to find out why.
      
    
      
    
        On the Go side, Fiber v3 turned the handler signature from a pointer into an
        interface (func(c fiber.Ctx) error), replaced c.BodyParser
        with the binding API (c.Bind().Body(&data)), moved static serving out
        of the app into a middleware (static.New("./uploads")), and changed the
        CORS config to take a function for allowed origins. On the React side, Router 7 has
        no Redirect or Switch and no props.match: every
        page that read an id from the URL became a useParams hook, and every
        post-save redirect became a rendered <Navigate>. React 19's stricter
        types pushed the API responses through explicit casts and the models into TypeScript
        classes and interfaces. None of it is glamorous; all of it is the difference between a
        tutorial and something that runs.
      
    
      
    
        The other thing that's mine is the documentation. Every Go file has a header comment
        and every handler says what it does and what it returns; the React components carry
        the same. Both READMEs were written from scratch — features, prerequisites, setup,
        the API surface, the data model — so that someone cloning either repository can run
        it without watching the course.
      
    
    
    
  
    

    



    
  
    
    
    
      
    What I'd change before shipping it
    
      
    
        This is a learning build and it reads like one in places. Having gone through every
        file to document it, this is the list I'd work from next, in order.
      
    
      
    
        
    
          Secrets in source. The JWT signing key is a constant in
          util/jwt.go and the database DSN is a literal in
          database/connect.go. Both belong in environment variables, and the
          repository history means the key should be rotated regardless.
        
    
        
    
          Authorisation coverage. As shown above, only the user handlers call
          IsAuthorized. Roles, products and orders should, and the check should
          answer 403 Forbidden rather than 401 — the request
          is authenticated, it just isn't allowed.
        
    
        
    
          Uploads. c.SaveFile(file, "./uploads/"+file.Filename)
          trusts the client's filename. It needs a generated name, an extension allow-list and a
          size cap.
        
    
        
    
          Money as float32. Prices and totals are floats, and the CSV export
          truncates them to integers. Cents as an integer column, or a decimal type, and a
          formatted export.
        
    
        
    
          Smaller things. The page size is a literal 5; the CSV
          export writes to a fixed path on disk before streaming it; and there are no tests.
          A handful of handler tests against an in-memory SQLite would have caught the
          truncation bug before this page did.
