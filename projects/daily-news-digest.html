AI-news: a personal daily digest that ranks the web against my interests

One scheduled job: fetch from a fixed list of AI, hardware and games sources, drop anything seen before, rank what's left against an interest profile, summarise the top slice, and write one Markdown page I read each morning instead of scrolling Hacker News. No app, no server, no UI — the page is the product.

Status: ongoing — phases 0 to 3a of 5 are merged, plus a full code review. The skeleton, all five sources end to end, the SQLite store with deduplication, and an interphase review that raised 54 findings and fixed 43 of them without moving a single row of the pipeline snapshot. Next is phase 3b: the rule-based ranker with per-topic quotas, then the rendered page. Started 2026-09-12 · last updated 2026-09-15.

What it is

A command-line program with four subcommands — digest fetch, rank, render, run — kept separate so that ranking can be iterated on without re-fetching. It reads two YAML files: sources.yaml (which feeds to pull, their weight, and a per-source fetch_limit) and interests.yaml (topics with keywords, per-topic quotas, anti-topics, hard rules). Everything it learns lands in one SQLite file; the output is digests/YYYY-MM-DD.md. Five sources, all live — Hacker News, GitHub Trending, Hugging Face daily papers, a bundle of six AI-lab blog feeds, arXiv cs.AI / cs.CL / cs.MA — and a firm rule not to add a sixth until the pipeline works end to end.

The pipeline is seven stages, each a pure function where it can be, each behind its own module with a one-line contract: 

fetch → normalise → store → rank → summarise → render → deliver

adapters/    only fetch and map to Item. No scoring, no DB, no LLM.
store.py     only reads/writes SQLite. No business logic.
rank.py      pure: (items, profile) -> scored items. No I/O.
summarise.py the only module allowed to call an LLM.
render.py    only turns selected items into text via a jinja2 template.

The layering is written into the repo's CLAUDE.md as hard constraints — no web framework, no ORM, no Docker, no queue, no new dependency without asking, no network access in tests — precisely so that an agent building phase 4 cannot re-litigate what phase 0 decided.

Phase 3a: probe before you build

The four remaining adapters were specified from memory of their APIs, so the phase began by probing every endpoint before writing against it — inventing hazards that don't exist would have cost as much as missing real ones. Three of the brief's assumptions didn't survive. arXiv titles were already clean: 0 of 270 cs.AI entries carried the arXiv: prefix or embedded newlines the prompt warned about, so the normaliser stays as a guard against older formats and a test pins the measurement so the comment can never drift into claiming a hazard that isn't there. arXiv volume was five times the estimate — 270 for cs.AI alone, 401 across three categories. And 38% of arXiv entries were revisions: a replace is a v2 of a paper that may be months old and would enter the digest looking brand new, so the adapter keeps only new and cross announcements, with a test asserting the revision share exceeds 25% so that deleting the filter explains what breaks rather than going quiet.

A mirror that is unreliable per feed is the worst shape, because one healthy feed tells you nothing about the others. Every alternative checked 404s, so the mirror stays; the three dead feeds were swapped for claude, anthropic_research and cursor — fresh, and weighted toward AI coding agents, the highest-weighted topic in the profile — and the dropped ones remain in sources.yaml as a comment with their measured ages, so "why is Mistral not here?" has a written answer. A follow-up commit moved each feed's staleness threshold into config beside its URL with the measured cadence as a comment, because one global number either cries wolf on slow feeds or sleeps through fast ones, and a warning that cries wolf gets ignored.

Two defects only the live run could catch

The blogs bundle imported its entire back catalogue — 1,824 items. Unlike arXiv, Hugging Face or GitHub, which publish a current list, these feeds serve years of history (openai_news alone: 1,193 entries), all of it permanently unselectable under a 48-hour max_age_hours. A 30-day entry cutoff gives fifteen times the headroom of anything that can ever be selected: 1,824 became 112.

That fix would have silently destroyed the staleness warning. A 112-day-stale feed has zero entries inside a 30-day window, so measuring staleness after the cutoff reports a bare "0 items" — which reads as a quiet week and loses exactly the signal the mechanism exists for. The newest-entry date is now computed over every entry before the cutoff, and a test asserts the note says stale rather than 0 entries. This was the project's fourth instance of the same shape — two individually correct changes blinding each other — and it became a standing review question in the plan: for every filter, what downstream measurement reads the filtered data, and does it need the unfiltered version?

When zero items is an error

Raise when zero means we no longer understand the endpoint; return empty when zero is a state the source can genuinely be in. GitHub Trending always has rows, so zero is selector rot or a 403 body and the adapter raises; the curated papers list likewise. arXiv returns empty but raises on a malformed feed; the blogs bundle returns empty per feed but raises if all six yield nothing; Hacker News simply returns empty. Per-feed diagnostics travel as data — a small drain_notes() extension to the adapter contract, since adapters may not log and neither Item nor SourceHealth can say "worked, but one of six feeds is four months dead" — and are drained in a finally so the six failure lines survive the all-feeds-dead error. Losing the diagnostics exactly when something went wrong would be the failure the mechanism exists to prevent.

The phase also produced its first cross-source duplicate in the live database: the same paper from Hugging Face and arXiv, two URLs that hash differently, caught by Dice and the digit guard. No winner was implemented — the phase was for the observation — but two findings went to 3b: both URLs end in the same arXiv id, so an extracted-id rule would catch every such pair exactly and deserves to sit above title similarity rather than be folded into canonical_url, where a collapse is a silent drop; and the current winner is decided by config ordering, which is not a decision.

The interphase review: eleven commits, no features

Phase 3a added four adapters to a pipeline whose shape had been decided while there was exactly one, and nothing had asked whether that shape survived. So before the ranker started, the whole codebase was reviewed along six dimensions — silent failure and observability, layering and coupling, duplication and the adapter shape, test-suite health, vocabulary and the error taxonomy, documentation drift — with every finding sorted into three buckets: improvable within the project's constraints; a constraint itself causing harm; or the constraint working and the obvious improvement being a regression. Fifty-four findings: 43 fixed, 10 deferred against a stated trigger, 1 won't-fix. Seven fix themes, one per session. The test suite went from 178 collected tests to 242.

The safety net came first

Before any review session ran, one commit built a characterisation snapshot: the real fetch → store composition over the recorded fixtures, dumped as 425 sorted rows with a hash of each raw payload. It asserts nothing about correctness — only that the composition has not moved — which is what makes it the contract a refactor can be measured against, covering what unit tests structurally cannot: cross-source dedupe, the direction of every dupe_of, four date formats arriving at one store. Its clock is pinned from the fixture manifest rather than a constant, because the blogs bundle filters against now − 30 days: freeze the clock and the first fixture refresh pushes every entry outside the cutoff, giving a snapshot of nothing produced by a test that still passes. It stayed byte-identical through a model split, six renames, a relocated cap, a replaced registry and a new error hierarchy — and regenerating it to make a red test green is forbidden, because that is a refactor with its evidence deleted.

The finding with the highest consequence

Every source could fail and the process still exited 0. Seven consecutive total failures would have satisfied the project's own "runs unattended for seven days" criterion while delivering nothing, and a scheduled job would have stayed green throughout. Fixed as an exit code read from the outcomes — 4 when every enabled source failed — and explicitly not by narrowing the catch that keeps one dead feed from aborting a run. Close behind it: the mandated one-line-per-source run log sat at INFO under a WARNING default, so the 07:00 scheduled run would have written it nowhere. Nobody types -v in a crontab.

The single finding against a constraint: CLAUDE.md's definition of done required digest run --dry-run to complete, and run was a stub that printed "not implemented" and exited 0 — so a change breaking every adapter satisfied the quality gate exactly as written. Worse than no clause, because it reads like end-to-end verification and displaces the check a session would otherwise improvise. It landed on its own commit rather than inside a refactor, because a governance change buried in a diff is hidden from whoever later asks why the gate moved.

Reports propose; diffs decide

The review document was derived from git show on the commits rather than from the reports, and the comparison is the most interesting result. Every finding and every fix-or-defer decision held. Five of the prescribed mechanisms did not: each moved toward something more conservative or more specific once the code was in hand — two of them corrections to the instruction rather than the finding, where the triage's suggested rename would have reused the exact word the adjacent finding was removing. A triage written from reports turns out to be directionally reliable and mechanically underspecified, and those divergences exist only because each theme had to propose a plan before it was allowed to write code. The triage got a dated amendment saying so, not a rewrite: it is a record of what was decided at the time, and the gap is the useful part.

Some of what the fixes found is in no report, only in the diffs. The fixture recorder hard-coded the entire Hacker News URL, so a config change would have left the snapshot built from a window production no longer used. An extracted date helper nearly turned malformed dates into absent ones — the item survives, nothing looks dropped, it simply never ranks — and was caught by a test written for a different finding. One edit silently never applied, and digest render mislabelled disabled sources as quiet for a whole theme, because the test called the helper directly with the argument the real call site was missing; that became a standing rule — a test that supplies the argument cannot prove the caller supplies it. And executing every command the README claims, as the last act of the last theme, found three false claims, including one written in that same commit.

Six findings are recorded as things not to improve, because the obvious fix is the regression: don't narrow the catch-all, don't make partial failure non-zero, don't fold the arXiv id into URL canonicalisation, don't strip source, don't exempt four-digit years from the numeric guard, don't merge the three 48-hour windows. The ten deferrals each carry a trigger written into the file where the work would be done — a docstring, a constant, a config comment — rather than only in a table that fires if someone rereads it.

Decisions worth defending

Most of the code exists because of a specific decision, and each pull request records the ones a reviewer should push on. The ones that shaped the store, all of which survived the interphase review — several are on its list of things not to improve:

"New" means digest_date IS NULL, never a date comparison

The obvious query — items whose first_seen_at falls on today — is wrong twice. The stored timestamp is UTC while the digest day is America/Vancouver, so a 07:00 local run sits at 14:00 UTC and a calendar-date comparison splits one morning's items across two UTC days, every day. And a date-based query permanently loses any day the run didn't happen: laptop asleep, Action failed, away for the weekend. Instead digest_date starts NULL and is stamped only when an item is rendered into a digest; a missed run then catches up by itself. There is a test that skips a day and asserts both days come back.

Dice, not Jaccard — and a numeric guard on top

At a 0.85 threshold Jaccard is barely reachable for real headlines: one extra word on a seven-token title already sits on the boundary, two words is a miss, so the check would have looked like it was working while almost never firing. Dice keeps 0.85 meaningful. But Dice alone has a false-positive class that lands squarely on this digest's subject matter — RTX 5090 Super vs RTX 5080 Super scores 0.875, and so do two model versions or two arXiv papers differing by a number. So titles whose digit-bearing tokens differ are never duplicates, whatever the ratio; and the guard is "token contains a digit" rather than str.isdigit(), because 7B, v2 and gpt-5 are exactly the tokens that matter and none of them is all digits. A test named test_the_numeric_guard_is_load_bearing asserts that the 5090/5080 and 4.5/4.6 pairs both score above threshold, so deleting the guard makes the suite say exactly what breaks rather than go quiet.

Strip only unambiguous tracking parameters

The original spec stripped source along with utm_*, fbclid and gclid. It was wrong: a bare source is an ordinary application parameter, and huggingface.co/models?source=trending and ?source=likes are two different listings that would hash identically. The failure is asymmetric and invisible — dedupe is INSERT OR IGNORE, so the second item is dropped with no row and no log line — while a false split merely shows a story twice. That asymmetry, seeing a story twice is recoverable, silently merging two is not, is the rule behind every dedupe choice in the project.

Timezone-aware or rejected

The Item model refuses a naive datetime rather than assuming UTC. feedparser returns naive structs, the HN API returns ISO with a Z, arXiv carries its own offset; silently assuming UTC is a multi-hour error nobody notices until the ranker sorts by recency and mixes the two. The store converts to ISO strings on the way in and parses back to aware datetimes on the way out, with a round-trip test on a +05:30 value — and the HN adapter takes its timestamp from the integer created_at_i, where awareness is structural rather than dependent on a suffix.

Two caps with two names

fetch_limit is per source and bounds ingest; quota is per topic and bounds selection. Giving them one name invites "which one binds?" bugs, so a test feeds a quota: key into sources.yaml and asserts it raises. Ingest is deliberately generous — arXiv 50, HN 30 — because every raw payload is kept in raw_json, unedited, so that when the ranker changes in week three it can be re-run over three weeks of history offline instead of waiting three weeks to see whether the change helped.

A 48-hour window, not 24

A 24-hour creation window permanently loses slow burners: a story posted 30 hours ago that crosses 100 points this morning was never inside the window on either run. Re-seeing yesterday's items costs nothing once the URL hash dedupes them. The lookback and the profile's max_age_hours currently share the value 48 and are annotated as two different things that must stay free to diverge.

What the work turned up

Each phase's pull request has a section with this title, because the bugs a phase finds in the phases before it are the most useful thing to record.

A test started hitting the network the moment fetch went live. A phase-0 test called main(["fetch"]), which quietly became a real HTTP call to Algolia — and passed, so nothing flagged it. The fix is structural rather than an assertion: tests/conftest.py installs a session-wide socket guard no test can opt out of. Two details came out of probing it. Loopback has to be exempt, because on Windows the asyncio event loop builds its self-pipe from a 127.0.0.1 socketpair and a blanket raise takes down the tests it exists to protect. And the guard's exception derives from BaseException, not Exception: recreating the regression showed it still passing with the guard installed, because fetch_all catches every Exception so that no source can abort a run — which turned the blocked connection into a recorded source failure and an exit code of 0.

That same catch was swallowing Ctrl-C. Chasing the question above exposed that fetch_all treated KeyboardInterrupt, SystemExit and CancelledError as "this source failed" — an interrupted fetch would have been recorded as a dead feed and surfaced as source rot in the next morning's health footer. Non-Exception BaseExceptions are now re-raised: the never-abort rule is about sources failing, not about the operator quitting.

A crash waiting for the first non-Latin-1 headline. sys.stdout is cp1252 on the Windows console, so printing a CJK or emoji title raises UnicodeEncodeError and takes down a job meant to run unattended at 07:00. Reproduced, fixed by reconfiguring stdout to UTF-8, and worth noting that a GitHub Action would never reproduce it — so the local run is the only thing standing between this and a silent morning failure. CLAUDE.md now carries an explicit encoding="utf-8" rule for all file I/O, since phase 3's open(path, "w") is the same bug on a different surface.

Algolia omits url on text posts — it does not send null. The adapter already fell back to the HN item page, but the first test asserted is None and failed against the real fixture. It is now pinned with a parametrised test over all three shapes (absent, null, empty string), so a future change from one to another can't reach the job as a crash.

The numeric guard failed six of its own tests, and was right to. The fixture pair was "…at CES 2027" vs "…at CES" — labelled a duplicate, but the numbers differ, so the guard rejected it. The titles were wrong, not the rule. And WAL-mode SQLite leaves -wal and -shm sidecars behind a killed process; they were not in .gitignore until a run was interrupted.

How it's made: one phase per session

The project has two design documents written before any code — a build plan (scope, the source catalogue with each endpoint verified by hand, the data model, the ranking design in three escalating versions, the phases) and an implementation guide that contains the literal prompt for each phase. Both are in the repo under docs/. The method follows from the JHA experience: every phase is a fresh Claude Code session, so nothing drifts, and CLAUDE.md carries the standing constraints across sessions instead of the conversation.

Each phase runs the same loop. Paste the prompt; it ends by asking for a short plan and a question or two the agent must answer before writing ("tell me one case where canonical_url could collapse two genuinely different URLs into one" — which is how the source-parameter decision above surfaced). Read the plan, push back, say go. When it says it's done, run the acceptance command myself — the tests with wifi off, the second fetch that must say new 0 — because this project is all I/O and I/O is where an agent's confidence is least calibrated. Then a review prompt in a fresh session, which reviews better than the one that wrote the code because it isn't defending its own choices. One pull request per phase, with the decisions and the findings written up in the description. Between phases, when the shape of the code has changed enough — five adapters where the design assumed one — the same discipline scales up into the interphase review above: a snapshot first, six independent review passes, a triage, then one fix theme per session, each proposing its plan before it may write.

The rules I police personally rather than delegate: no new dependency without asking (the token-set ratio, the CLI and config loading are all places an agent reaches for rapidfuzz, typer or pydantic-settings to avoid twenty lines); no network in tests; adapters stay dumb; and a scraper that can't parse raises rather than returning an empty list, because an empty list is indistinguishable from a quiet day and is precisely the silent rot the health footer can't catch.

Division of labour, plainly: the plan, the constraints, the phase boundaries, the acceptance checks and the review are mine; nearly all of the code was written by Claude Code against them. The decisions section above is a fair record of where the agent's first answer was changed and why.

Where it's thin

It doesn't produce a digest yet. Five sources in a database and a plain-text list of 428 unrendered items is an ingest layer, not a product. Ranking, rendering and the schedule are the part that decides whether this replaces Hacker News or becomes another feed I don't read; the plan's answer to that risk is four mornings of reading the rule-ranked output before any LLM code is written.

Near-duplicate detection has a known miss. Inflectional variants are different tokens, so a re-ordered headline — "Anthropic releases X" vs "X released by Anthropic" — scores 0.80 and passes as two stories. Stemming would fix it and is out of scope for v1; the trade-off is recorded next to the threshold.

The AI-blogs mirror is unreliable per feed. Three of its six feeds were months stale while returning HTTP 200 and well-formed XML, and every alternative checked 404s, so the mirror stays and the staleness warning is load-bearing rather than decorative. Conditional GET is implemented and tested but not persisted: the sources table has one etag column per source and the bundle needs six, so every request still goes out unconditional — deliberately not half-built until a host actually rate-limits the job.

Cross-source duplicate precedence is config ordering, not a decision. The arXiv copy of a paper currently points at the Hugging Face copy only because hf_papers precedes arxiv_cs_ai in sources.yaml; alphabetising the file would silently flip it. Phase 3b owes an explicit precedence and a test that reorders the file and asserts the winner doesn't move.

The review says what nobody looked at. Performance, concurrency beyond never-abort, year-scale data growth, database size and supply chain were out of scope, and the review document lists them so that "54 findings, all decided" is not mistaken for completeness six months from now.

Committing a WAL-mode SQLite file from a GitHub Action — the phase-5 plan — needs a PRAGMA wal_checkpoint(TRUNCATE) before the commit step, or the committed file can be missing the very transactions the run just made. Noted for phase 5, not yet handled.
