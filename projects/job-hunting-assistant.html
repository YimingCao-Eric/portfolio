Job Hunting Assistant: a multi-site job scraper with an LLM matching pipeline

Looking for work means reading the same postings on LinkedIn, Indeed and Glassdoor, each with its own search, its own filters and its own idea of what a "job" is. Job Hunting Assistant is the tool I built for my own search: a Chrome extension that scrapes all three through my logged-in session, a FastAPI backend that stores every posting twice — once as the site shaped it, once in a single canonical shape — and a React console to search, read and run the whole thing unattended. Since August a second repository, filter-matcher, reads that table and turns it into a short list worth applying to. Both are in active development; the figures on this page run the same code the backend and the extension run.

    What it is

    Three processes and a database. The extension does the scraping from inside a real browser session: content scripts read each site's job list, fetch the full description through whatever surface the site exposes, and hand each posting to a service worker that posts it to the backend. The backend ingests it, serves it back, streams scan progress over a WebSocket, and owns the state that lets the extension run for days on its own. The console is four pages: what to search for, the jobs, the scan logs with their debug traces, and the auto-scrape dashboard. Everything runs locally under Docker Compose; there is no cloud and no account but mine.

    Three sites, three different surfaces

    None of the three boards has a public API for this, and each one hides the full posting somewhere different. The scraper for each is its own set of content scripts, and the interesting work in every one was finding the surface that returns structured data instead of parsing rendered HTML.

    LinkedIn renders its job pages from an internal REST API called Voyager. The page's own JSESSIONID cookie doubles as the CSRF token, so the content script reads it from document.cookie, then requests /voyager/api/jobs/jobPostings/{id} with the same decorationId the site uses and gets the complete WebFullJobPosting entity back as JSON — title, description, salary, workplace type as an enum URN, industries as resolved entities. Two attempts, and a 429, 403 or LinkedIn's non-standard 999 gives up on the posting rather than retrying into a ban.

    Indeed ships the search results as a "mosaic" data blob embedded in the page, which gives the job keys and the card-level fields; the description comes from a GraphQL endpoint at apis.indeed.com that needs the page's API key in a header. The query asks for exactly the fields the schema stores — attributes, location, compensation with its unit of work, language — so the per-source row is the API's answer, not a parse of it. The Indeed scripts went through six fetch strategies before settling on this one; the file is still called rate_strategy.js.

    Glassdoor is the messiest: the listing page sometimes carries a __NEXT_DATA__ block, sometimes only JSON-LD JobPosting schema, and the two disagree about salary provenance. Every Glassdoor detail fetch was failing — zero rows, every scan — and the diagnosis came from a DevTools log: the fetch went to a locale subdomain (fr.glassdoor.ca) while the page sat on www.glassdoor.ca, so the browser blocked it as cross-origin. Pinning the request to the page's own origin was the whole fix.

    On scraping. This is personal tooling, and it's built to stay that way: it runs in my own browser under my own login, paced like a person scrolling — two to four seconds between scrolls, thirty between scans — it probes each site's session before every cycle and stops the moment a board answers with a challenge, and nothing it collects leaves my machine. It exists so that I read each posting once instead of three times. It isn't a product, it doesn't redistribute data, and I wouldn't run it as either.

    Store it twice: the site's shape and ours

    The first version of the schema had one LinkedIn-shaped table and tried to fit Indeed and Glassdoor into it. It didn't fit, and the console ended up reading an empty table while real scans wrote elsewhere. The rebuild in July made the split explicit. Every ingest writes two rows in one transaction: a per-source row in linkedin_jobs, indeed_jobs or glassdoor_jobs — append-only, unnormalised, faithful to what the site said, with the raw payload as JSONB — and a canonical row in scraped_jobs, 27 columns in one shape that the console and any future consumer read without a per-site join.

    All normalisation lives in the projection, and it follows three rules that took a real scan to get right. NULL means the site didn't say. Never "no", never a default: Glassdoor has no remote boolean, so remote is true when it lists remote work types and NULL otherwise — never false. Closed vocabularies with precedence. employment_type is one of seven tokens; a posting tagged both Full-time and Part-time yields FULL_TIME and the other survives only on the per-source row. Unknown values warn, recognised no-ops don't. A token the table has never seen logs a warning, which is how the vocabulary corrects itself from live data; a site saying OTHER is a correct answer that maps to nothing and stays quiet, so it can't bury the warnings that matter. 

    # The one place the projection knowingly asserts more than the site said.
def _indeed_workplace_type(remote_location: Any) -> str | None:
    """Not a tri-state pass-through: False becomes ONSITE, an assertion Indeed
    did not quite make. Indeed cannot express hybrid, so a hybrid posting is
    recorded ONSITE — accepted so on-site filters return Indeed results at all.
    Read ONSITE here as "not remote", not as confirmed on-site."""
    if not isinstance(remote_location, bool):
        return None
    return "REMOTE" if remote_location else "ONSITE"

    Two of those tokens came from data, not design. The first scan after the filter columns shipped logged projection_unknown_employment_type for Indeed's "Permanent" and projection_unknown_salary_source for its "EXTRACTION". Permanent is a tenure axis, not an hours axis — a permanent part-time job exists — so it became its own token ranked below the hours tokens, and the common "Full-time, Permanent" still yields FULL_TIME. EXTRACTION means Indeed parsed the pay out of the employer's own description, so it counts as employer-disclosed. Both decisions are in the module's comments with the date of the scan that forced them.

    The trap the process caught. Ingest uses ON CONFLICT DO NOTHING, so a canonical row is never recomputed. After the LinkedIn workplace fix, the dashboard showed "LinkedIn workplace = 0" and it looked like a regression. Replaying the stored payloads through the projection gave REMOTE 180 / HYBRID 123 / ONSITE 76 — the code was right, the old rows were stale, and they'd heal on their own within one shelf-life. The recipe for telling those two cases apart — replay first, scan never — is now in the feature's quickstart.

    Run the orchestrator, one cycle at a time

    probeSiteSession, preCycleCheck, the auto-pause counter and scheduleNextCycle from extension/background/auto_scrape.js, ported as they are. Set what each board's probe would return, press run, and watch the state row.

      Two rules worth seeing. A bare 403 is treated as rate-limiting, not a CAPTCHA — only a challenge URL or a recognisable challenge body earns that label, because a CAPTCHA requires a human and a rate limit just requires patience. And a 5xx or a thrown fetch is treated as live: a board being down isn't evidence that my session died, and pausing on it would leave the orchestrator stuck every time a site had a bad minute. Set the backend to "down" and run three times to see the auto-pause.

      Keeping a service worker honest

      A Manifest V3 service worker is killed whenever Chrome feels like it, so an orchestrator that runs for days can't keep its state in memory. Every cycle starts by writing cycle_phase: scrape_running to a state row on the backend and ends — in a finally — by writing it back to idle. The worker also polls that row every 30 seconds and only re-arms its own alarm when the phase isn't running and no alarm exists, which is what stops a restarted worker from starting a second cycle on top of the first. The state row carries a heartbeat with an instance id, so the dashboard can warn when two copies of the extension are alive in the same five minutes.

      The smaller rules came from watching it fail. Repeated pre-check failures auto-pause the orchestrator instead of retrying forever. A cycle that finishes in under thirty seconds with nothing succeeded gets a five-minute cooldown, because "nothing worked, try again immediately" is exactly the pattern a board would block. On graceful exit and on worker startup, any popup window that looks like a job-board scrape gets closed, so a zombie popup can't keep scraping or attach itself to the wrong run log. And progress is mirrored to the backend and fanned out over a WebSocket, so the console's scan page updates live without polling while a run is in flight.

      Long runs find the bugs short tests can't

      The orchestrator's first ten-hour soak, in late April, was a catalogue. A config_change_pending flag that nothing ever cleared aborted 254 of 255 cycles. Every HTTP 403 was classified as a CAPTCHA, so Indeed was suspended for 191 consecutive probes over what was only rate-limiting — hence the rule above that a bare 403 is patience, not a human. A thirty-second window between "decide to start a cycle" and "record that a cycle started" let twelve cycles begin in one hour, with three popups scraping LinkedIn at once; writing cycle_phase: scrape_running as the very first line shrank the window to about fifty milliseconds. And zombie popups from earlier cycles attributed 207 Indeed jobs to a LinkedIn run log, which is why startup now closes any popup that looks like a scrape. The five-hour validation run after the fixes completed eight of nine cycles with 984 LinkedIn and 65 Glassdoor jobs and zero attribution mismatches.

      The one I'd tell in an interview is cycle 455. The dashboard reported zero of nine scans succeeded — and 949 new LinkedIn rows. The cause was a five-minute "stale scan" cleanup threshold firing on perfectly healthy 33-minute LinkedIn scans (39 pages, 915 jobs), then a later status write flipping failed back to completed while leaving the error message in place. It had been silently firing since May 4. The fix was two lines; the lesson in the notes is one: observability lies are worse than runtime bugs. Cycle 481, after the fix, ingested 1,306 jobs at nine of nine.

      Two smaller ones shaped the code more than their size suggests. Ingest looked up postings by description hash with scalar_one_or_none(), and because reposts and ATS templates legitimately share a hash, six to ten percent of LinkedIn ingests were returning HTTP 500; one method change took new jobs per scan from about a hundred to about 240. And the extension's original setInterval poller simply died when Chrome suspended the service worker after thirty idle seconds, so "Scan" did nothing until you touched a tab — the reason everything is now driven by chrome.alarms.

      How it was made: spec-first, with Claude Code

      The first four months were built the ordinary way with an AI coding agent in the loop, and by July the result had the shape that produces: a lot of working code, three styling systems in the frontend, a matching pipeline whose state machine lived in nullable columns, and a README that described a system that no longer existed. The rebuild that followed was a deliberate exercise in spec-driven development using GitHub Spec Kit with Claude Code as the implementer — starting from never having used it.

      The loop for every change was the same: constitution → specify → clarify → plan → tasks → analyze → implement. The constitution is a short document of the project's actual rules — every schema change through Alembic, per-source tables append-only, dual-writes atomic, background work in a fresh session, the smoke tests are the behavioural contract, change surgically. Before changing anything, the agent wrote as-built specifications of five modules as they actually behaved, each with a verification pass against the source and an optimisation backlog. Then five feature specs took the system from there to here: the search-only split, the Glassdoor fix, the unified table, the frontend rebuild (94 tasks), and the filter columns (48 tasks). The companion service was built the same way from a blank repository: its own constitution, one 146-task spec, and six domain checklists — boundary, cost, dedup, fidelity, integrity, requirements — whose resolutions are recorded as dated clarifications in the spec itself.

      What I'd say to someone sceptical of this way of working is that the specs are where the engineering judgement lives, and that's where the work moved. The projection's vocabularies were marked "reasoned, not observed" in the spec, with a required review of the warnings from a live three-site scan before the feature could close — and that review found that the LinkedIn fixture the agent had written assumed localised labels ("Remote", "Hybrid") when the live payload sends bare enum URNs. The fixture was, in the module's own words, fiction; the process was designed so that fiction couldn't ship. The frontend rebuild put a real tsc and ESLint gate in front of every task, including a custom lint rule that bans calling the consume-and-clear /extension/pending* routes from the UI, because those routes are a trap that a future page would fall into.

      The working rules I hold the agent to are written into both constitutions, and they came from being burned. Read the clause, not the summary. Verify on real data, not inference — a code survey cannot see state; only a query can, and more than once the agent reported "implementation complete" for a change that never made it into the running container. No vacuous green — a skipped assertion is a failure, because a checkmark that never ran ends the search for the bug. Bound the scope — rot found in another repository gets flagged in the spec, not fixed on the way past. And before any large change, ask. The plan for the matched-claim mechanism went through six conflict scans against the live repository before implementation — 13 issues, then 8, 3, 2, 2, 0 — and every one of those 28 findings was cheaper to fix in a document than in code.

      What the agent did and what I did. Claude Code wrote nearly all of the code in both repositories, the specs, and the notes I've drawn on for this page. I set the direction, wrote and ratified the constitutions, and made every design call the specs record as a clarification: I rejected the "purer" claim design for the simpler column-on-the-table; I replaced an eighty-line failed-ingest replay buffer the agent had built with a ten-line halt-and-report, because the cards are still on the source page and tomorrow's scan picks them up; PERMANENT is a token because I said it was a tenure axis. I ran the ten-hour and five-hour soaks, read the warnings from the live scans, and force-stopped runaway cycles in SQL when I had to. The bugs on this page were found by me running the thing on my own job search. I think that's the honest division of labour in 2026, and I'd rather state it than have a reader guess.

      The half that left, and came back as its own service

      Until July, JHA also de-duplicated postings and matched them against my resume: a three-pass dedup (metadata gates, description gates, then exact-hash and TF-IDF cosine duplicate detection) and a four-stage matching pipeline (CPU extraction, hard gates on years, salary, degree and visa, a CPU pre-score, an optional gpt-4o-mini re-score). It worked, and the as-built specs made the case for removing it anyway: its state machine was implicit in nullable columns, it only ever ran against the old LinkedIn-shaped table, and not one test covered its eligibility rules. The search-only split deleted it outright, and the canonical table got a matched flag that nothing in JHA sets.

      filter-matcher is where it came back, in August, as a separate repository with its own constitution. It is an on-demand CLI — python -m filtermatch run [--limit N] [--cpu-only] — that reads only scraped_jobs, claims a batch with WHERE matched = FALSE (flipping the canonical row and its per-source origin in one transaction, the single write it ever makes to JHA's data), and pushes each posting through stages ordered strictly cheapest-first: the five profile preferences, a completeness check, the field gates, duplicate detection, CPU skill extraction and gates, and then coverage banding before any AI call. Coverage below 0.50 is rejected without spending a token; exactly 1.00 is shortlisted as cpu_perfect; only the ambiguous band in between goes to the model. It writes to five stores of its own — the shortlist, the exclusion audit, a blacklist re-entry ledger, a skill-candidate table, and a run record — and every run ends by reconciling its counts: claimed must equal shortlisted plus excluded plus anomalies, or the run is recorded as failed. 

      # pipeline.py — why the completeness check runs before the language gate.
# Measured, 2026-08-07: langdetect on two characters returns Hungarian at
# confidence 0.999994; "Job posting." returns Tagalog at 0.999996. Short text
# does NOT produce low confidence -- it produces spuriously HIGH confidence on a
# wrong language. So a truncated posting reaching the language gate first would
# be recorded as (field_gate, language_mismatch) with a fabricated verdict,
# instead of (cpu_gate, incomplete_posting), which is what it actually is.

      The cost discipline is a constitutional principle with seven numbered rules, and the design is built around them: cheap gates before any model call; only the ambiguous band ever spends judgment tokens; every job description is compressed to a 120–200-word standardized_jd once, which cuts input tokens by roughly 70%; prompts are ordered static-first so the provider's prefix cache discounts the repeated half; and skills are extracted by a CPU alias vocabulary, never by the model. A fifteen-cell outcome matrix in the spec governs every combination of coverage band, mode and AI result — fourteen reachable, one proven structurally unreachable — and the shortlist records which of four decision methods produced each entry, so that, in the spec's words, a shortlist full of cpu_tiebreak is recognisable as an AI run that silently lost its AI.

      The spec is 104 requirements, 25 success criteria and 43 recorded clarifications, and the live-data review it demanded earned its place. The vocabulary the spec assumed for pay periods was YEARLY; the live table says ANNUAL, and 28% of postings would have quietly become "salary uncomparable". Glassdoor writes skill lists into its experience-level field, so a plausible experience gate would have excluded 56% of the corpus. And the design's assumption that about half the backlog was claimable was wrong in the other direction: all 113 live rows were. The constitution's fourth principle — a false keep shows one extra card; a false drop hides a real opening — is why every one of those became "keep and count", never "exclude".

      Five migrations, 184 tests across five smoke suites with every AI path mocked, and 137 of 146 tasks done. The nine that aren't are honest ones: three items are blocked on live data — the service drained every claimable posting (113 of 113) during development, so a real AI-mode run, a real cpu_strong shortlist and a real cross-post collapse each wait for the next three-site scan. Building it also surfaced a trap worth recording: its skill-candidate migration collided with a table JHA's own migration 017 had left behind — 7,976 frozen rows with no living code — and the fix was a rename plus a new rule that every store name is asserted free at migration time, so the next collision is a named abort rather than a puzzle.

      Where it's thin

      The scrapers have been idle since July. The extension's last heartbeat is from the day the search-only rebuild finished; everything since has been the companion service, built against the July corpus. The README was stale for the same reason and has been rewritten in the current working copy — that rewrite, and the docs move into docs/, are not yet pushed.

      Glassdoor's workplace_type is always NULL because the scraper doesn't yet capture remoteWorkTypes. The projection is right and will populate the moment the extension supplies the field — but a consumer that filters remote on workplace_type instead of remote silently drops the whole Glassdoor corpus.

      Testing is asymmetric. The frontend has 135 unit tests; the backend has four smoke scripts that need a running Compose stack and one unit test on the projection. The projection deserves a proper parametrised test suite, and so do the ingest routes.

      Single-user assumptions everywhere. Auth is one bearer token (dev-token), config is a JSON file, the orchestrator state is a singleton row. All correct for one person on one machine, all wrong for anything else — which is fine as long as it stays one person on one machine.

      Small things on the list. GET /jobs orders by scrape_time DESC with no tiebreaker, so page boundaries can repeat a row; the constitution still enumerates test filenames and drifts when one is added; and two frontend checks (the 360-px layout and the unsaved-changes guard) still need a human in a real browser.
