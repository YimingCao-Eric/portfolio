Meeting transcription → a real-time "external brain"

Start with a meeting transcription tool built on MOSS-Transcribe-Diarize; grow it step by step into a real-time assistant that listens to a conversation, invokes tools or deep reasoning automatically, and hands you the answer fast enough to use mid-conversation — an external brain.

Status: Recorded. This is an outline, not an implementation — recorded so the idea and its open questions aren't lost. It will change as I think it through. Created 2026-09-12 · last updated 2026-09-12.

Core idea (in my words)

  • Step 1 is concrete and bounded: a meeting transcription tool (transcript + who said what) using the open-source model.
  • The ultimate direction is undecided. One candidate: the system processes conversation content and automatically calls tools or performs deep reasoning to assist the user during negotiations or discussions.
  • Motivating use case (imperfect, but captures the point): a stranger unfamiliar with smartphones asks you for directions. You want to help but don't know the exact route. The moment lasts a second or two — no time to pull out a phone, open Maps, search, and translate the route relative to where you're both standing. Smart glasses hear the question, automatically compute the optimal route, and let you describe it within one or two seconds. The scenario assumes you can't do the manual steps yourself (constraints or lack of time) — that constraint is the crux.
  • Honest self-assessment: the full vision is complex, I lack some of the expertise, and feasibility is uncertain. So: build the transcription tool first, then upgrade gradually toward real-time and extra features.

Proposed roadmap

Phase 1 — Offline meeting transcription tool (the real first step)

  • Run MOSS-Transcribe-Diarize locally on recorded audio; output a diarized transcript (speaker labels + timestamps).
  • Evaluate: accuracy on English and Chinese, mixed-language meetings, hardware requirements (GPU? CPU-only feasible?), latency per minute of audio.
  • Add LLM post-processing: speaker naming, summary, action items, decisions.
  • Deliverable: CLI or minimal web app that takes an audio file and returns a clean meeting note.

Phase 2 — Streaming / near-real-time transcription

  • Chunked or streaming inference; measure end-to-end delay.
  • Live transcript view; rolling summary that updates as the meeting proceeds.
  • Decide whether the MOSS model supports streaming well enough or a different ASR front end is needed for the live path (keep MOSS for the high-quality offline pass).

Phase 3 — Conversation understanding + tool triggering

  • Intent detection on the live transcript: "is there a question here the user can't answer instantly?" (directions, a fact, a number, a date, a translation).
  • Tool router: maps detected needs to tools (maps/routing, search, calculator, calendar, translation).
  • Output must be speakable: a one-sentence answer the user can say out loud, not a page of results. For directions: relative to current position and heading.
  • Latency target: answer within ~1–2 s of the question ending. This is the hard constraint that shapes everything (small fast models for detection, pre-warmed tools, speculative execution).

Phase 4 — Wearable / glasses delivery (far future)

  • Smart-glasses or earbud form factor; audio in, text/audio out.
  • Privacy: on-device or at least user-controlled; consent for recording other people.

Key questions

  • What is the minimum viable "external brain" demo that proves the loop (hear → decide → tool → speakable answer) even if latency is 5 s at first?
  • Which tools are worth it first? (directions is the flagship example; translation is probably the easiest real win.)
  • How to avoid the assistant interrupting or answering when not wanted (push-to-ask vs. always-on suggestions).

Tech notes

  • Python; MOSS model per repo instructions; LLM for post-processing and intent; later a fast small model for the live path.
  • Personal hardware: check whether my home cluster / laptop GPU can run the model.
