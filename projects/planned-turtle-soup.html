Turtle Soup: a lateral-thinking puzzle game run by an LLM

A yes/no question-and-answer riddle game run by an LLM pipeline (or agent), where the LLM generates scene images and sound effects in real time as players uncover each part of the solution — so every session is unique and LLM unpredictability becomes a feature, not a bug.

Status: Next up. This is an outline, not an implementation — recorded so the idea and its open questions aren't lost. It will change as I think it through. Created 2026-09-12 · last updated 2026-09-12.

Core idea (in my words)

  • Players guess the hidden story behind a strange scenario by asking questions; the host answers "yes / no / irrelevant".
  • As players gradually figure out each part of the solution, the LLM generates distinct scene images and sound effects in real time to build atmosphere.
  • Every playthrough is different. The inherent randomness of LLM generation — normally an engineering drawback — is an asset in a game.

Why it's interesting

  • Turns LLM non-determinism into replay value.
  • Small enough to ship as a solo project; large enough to exercise the full multimodal stack (text → image → audio → orchestration).
  • Directly reusable as the engine for the Historical Time-Travel Simulator (idea 02).

Proposed system outline

Roles / components

  1. Puzzle Author — generates or selects a puzzle: surface story, hidden truth, and a list of "solution fragments" (the 4–8 facts a player must uncover).
  2. Host / Judge — answers player questions strictly yes / no / irrelevant, grounded in the hidden truth; never leaks. Tracks which solution fragments have been revealed.
  3. Progress Tracker — after each Q&A turn, diffs the player's known facts against the fragment list; emits "fragment unlocked" events.
  4. Scene Director — on each unlock, writes a short visual + audio prompt consistent with everything already revealed (keeps a running "scene bible" so images stay coherent across the session).
  5. Media Generators — image model (scene illustrations) and sound-effect / ambient audio model; possibly TTS for the host voice.
  6. Game Client — chat-style UI; shows the current scene image, plays sfx, shows the question log and a "how close are you" meter.

Pipeline vs. agent

  • Start as a fixed pipeline: Host → Tracker → Director → media calls. Deterministic control flow, LLM only inside each box.
  • Upgrade to an agent only if needed (e.g. Director deciding whether a scene change is warranted, or choosing between image / sfx / nothing).

Key design questions to resolve

  • Puzzle source: hand-written classic puzzles vs. fully LLM-generated puzzles (generated ones need a consistency check so the story is actually solvable).
  • Latency budget: image generation can take several seconds — pre-generate likely next scenes speculatively, or generate in the background and swap in when ready.
  • Consistency: how to keep the same characters/locations across images (scene bible, seed reuse, reference-image conditioning).
  • Judge reliability: yes/no answers must be correct; consider a structured hidden-truth representation (facts list) rather than free text so the judge is checking against data.
  • Multiplayer or single-player first? (single-player first; multiplayer is a UI/state problem, not an AI one).
  • Cost per session (image + audio calls per unlock).

Milestones

  1. Text-only MVP: one hard-coded puzzle, Host answers questions, Tracker detects fragment unlocks. CLI is fine.
  2. Add Scene Director + image generation on unlock; measure latency and coherence.
  3. Add sound effects / ambient audio; add TTS for host if it feels good.
  4. Puzzle Author: LLM-generated puzzles with a solvability check.
  5. Web client; session replay / share a "story so far" image strip.

Tech notes (initial guesses)

  • Python orchestration; Claude/GPT-class model for Host/Director; image API (e.g. Flux / Imagen / DALL·E-class); audio API (ElevenLabs sfx, or an open model); FastAPI + simple web front end.
  • Structured outputs everywhere so game state is data, not prose.
