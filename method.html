Method · how I build software with AI agents

Rigor has a phase: how I build with two AI agents

I build my own projects with two AI agents and a written method. One agent plans with me and writes every document; the other writes every line of code; I decide, use the product, and commit. The method decides where rigor goes — very little while the code is a throwaway prototype, all of it where the code is meant to last — and in between, a stage where the product is used every day and then measured with its code frozen.

A working document. First written on 18 September 2026, rewritten on 25 September from a week of running it on My Daily News, consolidated on 27 September and amended on 28 September. Every rule is stated with its reason, because a rule whose reason is forgotten gets re-litigated. Last updated 2026-10-04.

Stage 0 · Idea

Not a phase. An immature idea is written down — a paragraph, a note, not a document — so that it is not lost.

Who
Me alone.
Produces
A note in my ideas folder.
Rules
None: no structure and no exit test.
How it ends
I decide to start, and starting means opening Phase 1.
My Daily News
A note that began as “a personalised Hacker News for everything I follow”, with AI as the first field.

Phase 1 · Hypothesis

In conversation with the planning side, the idea becomes a product that exists only on paper: what it does, what it does not, what it believes about the world, and what would prove each belief wrong. Nothing is built. A question a demo could settle more cheaply than more thought is marked for Phase 2 instead of argued.

Who
Me and the planning side. No coding agent, no code.
Produces
PRODUCT.md — the first-run sentence (what the demo has to show on its first run for me to say “that's the idea”), the shape, every hypothesis with the test a demo would have to fail to refute it, the foreseeable problems, what is out of scope; then Pending and Open, always last. PLAN.md — how each later stage will be worked, so that Phase 2 starts from a plan rather than from momentum.
Rules
A belief without a refutation test is an assumption, and is listed as one.
How it ends
A five-point test, run by the planning side rather than merely confirmed by me: every hypothesis has a test a demo can perform; every foreseeable problem has an answer or is marked for Phase 2; the first-run sentence follows from the shape alone; the last full pass added nothing a demo could not settle faster; the plan names the environment decision as Phase 2's first act. I accept the paragraph recording the result — the paragraph, not the phase.
My Daily News
Closed on 18 September with the product on paper: the first-run sentence, and each belief with the result that would refute it.

Phase 2 · Prototype

It opens by choosing the production environment — stack, runtime, where the code runs — judged on suitability for the project alone, never on anyone's familiarity with it. Then a prototype is built fast to check the product document against facts, and the document is corrected in the same pass as each correction to the product. The prototype implements and tests features; only what needs elapsed time, unattended running or data that does not exist yet is deferred, with the reason written.

Who
All three, from the first session.
Produces
A working prototype in lab/, kept as reference only; PRODUCT.md corrected as it goes; one log, written by the planning side.
Rules
Loosened: the behaviour is reviewed, not the code; forks come to me only when product behaviour is at stake — names, libraries and layout are picked by whoever is closest and recorded. Strict, the control fence: prototype code never becomes the codebase; every claim about data is measured before it is stated; tests never touch the product's real data, enforced by a tripwire that hashes the data before any test runs; a snapshot before anything destructive; no keys in the repository.
How it ends
Every hypothesis has been measured, or deferred to Phase 2.5 with its reason written. The log closes.
My Daily News
Ran to about thirty sessions where the plan had said a handful — which is why session budgets were taken out of the method.

Phase 2.5 · Use, then measure

Some beliefs need days of use to test, and the prototype that leaves Phase 2 never quite matches the vision. Stage 1: use it every morning and fix what the use shows the same day. Stage 2: freeze the code and measure, each measurement against a threshold fixed before its data existed. Figure B, below, runs these rules day by day.

Who
All three; sessions are named by day.
Produces
A daily log, one section per date, frozen once the next day begins; the measurements' verdicts; then SPEC.md, written from what the prototype showed, every requirement traceable to something observed.
Rules
An issue found on a day is resolved that day, or marked “carried” with its reason. Stage 2 begins after a day of use with no finding that needs a code change and nothing landing after it. Any code change restarts the count. The freeze is checked before each measured day is accepted.
How it ends
The verdicts are reported — a measurement with no verdict is a result, stated with its reason — the specification is accepted, and the boundary question is answered in writing.
My Daily News
Stage 1 from 24 September — four mornings of use, the first with ten findings. Stage 2 from 28 September — the code frozen and five mornings measured against bars written down before the data. One belief has already landed below its bar, and the fail stands.

Phase 3 · Build

A fresh start from an empty tree, on a deterministic architecture, written from the stabilised specification. The prototype is reference and is never promoted. Where the prototype was vibe-coded with the agent in full control, here people review and modify the code.

Who
All three, with the code reviewed by people.
Produces
The product's codebase.
Rules
The strict rules suspended for the prototype return: one decision per diff, forks raised before code, and every prompt recorded verbatim in the log.
How it ends
As at every boundary, with the boundary question answered in writing.

Phase 4 · Deploy

The product is published and run for real.

At launch
The product's tree is made clean: lab/ and docs/ leave it in a single commit, so a clone gets only the product. The history keeps them — the goal is a clean product, not a hidden process.
Rules
The ones that hold everywhere: no keys in the repository, backups at defined points, the boundary question at the end.

Why there is a method

My Daily News is my third attempt at the same idea, and the first two failed in opposite directions. The first followed a plan step by step with a coding agent implementing each step. It produced working code, but as the code grew my review went shallow, and I lost control of where it was going. The second applied strict rules everywhere — probe before building, every design fork checked against real data, one decision per change, a complete written record. Control never slipped, and in three days it produced no demo: the rules were right, and they were spent on throwaway code. What I wrote down afterwards was one line.

"Rigor has a phase."

The method is that sentence worked out in detail. It separates the one who decides from the agent that plans and the agent that codes; it separates the documents that say what the product is from the ones that record how it got there; and it says, phase by phase, which rules are loosened and which never are.

Three actors, and what each owns

Me

Decides, uses, commits

I decide what the product is, use it, judge every report, and make every commit.

Deterministic work — a fetch, a command whose output is fixed and knowable — defaults to me, because an agent doing it costs tokens and can hallucinate. It goes to the coding agent when splitting it out would break a task's continuity.

The planning side

Claude in Cowork

Thinks with me and owns every document: the product document, the plan, the logs, the boundary paragraphs, the coding agent's prompts, and the repository's CLAUDE.md.

It may read any file, measure data with its own scripts, and move and back up files. It never runs, modifies or verifies the product's code.

The coding agent

Claude Code

Owns the code: writes it, runs it, tests it, and reports. It does not commit and does not write the planning documents.

A defect it finds in a document is reported, decided by me, and fixed by the planning side. It is absent until Phase 2.

The boundary is the product's code, not the filesystem, and the reason is the point of the whole arrangement: work done on the code outside the agent's loop is unrecorded, and an unrecorded change is a black box. Because the planning side never touches the code and the coding agent never writes the documents, every change to the product passes through a written prompt and a written report.

Three kinds of document

The split removes an ambiguity: a product document that also records how it came to say what it says stops being readable as a product document. So PRODUCT.md states what the product is, with nothing superseded left standing, and always ends with two sections in the same order — Pending, everything outstanding with the stage it waits on, then Open, the questions waiting on a decision. Every dated derivation, costed option and reversed recommendation lives in a log.

Every document from Phase 1 on lives in the repository's docs/. Prototype code lives in lab/, versioned so that every session is a diff, with its data kept out of git because it holds session cookies, tokens and personal records. CLAUDE.md is written by the planning side and read by the coding agent at the start of every session. Backups go outside every repository, each with a hash manifest, so a bad command inside a repository cannot reach them.

One session, from prompt to commit

  1. The planning side writes the prompt at the moment it is used, never in advance, as one copyable block, and I paste it.
  2. The coding agent works, and reports in five fixed parts.
  3. The planning side checks the report against the files it describes, verifies every number it intends to reuse, updates PRODUCT.md in the same pass, and writes the session into the log — including what it got wrong itself.
  4. I commit.

Every prompt names the real paths of the documents to read, says do not commit, says never read, print or echo .env, requires a snapshot before anything destructive, and ends by asking for anything found that was not asked about. A prompt that changes how a key, path or field is derived names every reader of it; a prompt that removes something records what would have to change for the removal to be wrong.

Every report has the same five parts: what ran, and where the snapshot is; what it showed, with numbers — never “tests pass”; the choices made where the prompt left them open; anything found that was not asked about, and anything in the prompt that turned out to be wrong; and one line confirming that nothing was committed and no document was touched.

Phase 2.5: use it, then measure it

Some beliefs cannot be tested at once — they need days of use, elapsed time, or data that accumulates. And the prototype that leaves Phase 2 never quite matches the vision: its first real use produces findings. So between the prototype and the build there is a stage of its own, in two parts, and the reason for the order is one sentence:

"A freeze is a claim that the thing is finished enough to measure."

Stage 1 — daily iteration. The prototype is used every morning and changed the same day in response to what the use shows. An issue found on a day is resolved that day; where it is not, the log says “carried” and gives the reason, because a carried issue is a decision, not an oversight, and has to look like one. Once a new day begins, the previous day's section is frozen. Nothing is measured here: editing the page writes real events into the product's own usage log, indistinguishable from a reader's. While the code moves, the instrument records the author.

Entry to stage 2. A day qualifies when using the product produced no finding that needs a code change, and no code landed after it. A finding means a finding from use: a defect caught by a test or in the agent's report does not disqualify the day, because a defect caught by a test is evidence that the process works.

Stage 2 — stabilisation. Nothing that changes the code under measurement happens. Each measurement runs against a threshold fixed before its data existed — a rule chosen once the numbers are visible is a description, not a threshold — and a measurement that yields no verdict is a result, reported with its reason. Any code change returns the process to stage 1 and the count starts again. Restarting is cheap by design, so it is done rather than argued about. Before each measured day is accepted, the freeze is checked: a diff against the tagged stage-boundary commit, and a hash manifest for anything git does not hold.

One rule was added by running it. On the evening the last stage-1 fixes were ready, the choice was between landing them and spending another day of use before the freeze, or landing them and measuring the next morning. My answer is now in the method:

"If a modification is required, the stabilisation will simply be postponed by another day."

So the first reading after the last change may count as measured morning 1, provisionally: it stands only if its use finds nothing to fix and no code lands after it. The restart rule holds exactly, and the changed product is still read once before any measured day stands. When the product has stabilised, SPEC.md is written from what the prototype showed — not before.

    Rules that hold at every stage

    Every planning reply has three parts

    Boundary check — the phase, the stage, and which exit criteria hold and which do not. What changed — by file, then by section. Your next steps — only what exists nowhere but in my head or hands; anything the planning side can read or run itself is not handed to me.

    A fork is raised only when it matters

    Only after the options have been run against real data and shown to differ; identical results mean the planning side picks, records the measurement and moves on. A fork arrives as options with their costs and one recommendation — never a question that has already chosen its answer.

    Decision rules come before numbers

    Any rule that will be read against a number is fixed and written down before the number exists.

    Backups at defined points, never ad hoc

    Before any session that deletes, migrates or repairs data; before any reorganisation of the documents; at every phase or stage boundary — each with a hash manifest. A backup taken because someone happened to think of it is not one the method can rely on.

    References name something stable

    A pointer from outside a document names the session that made a change, or a rule by its name — never a row or section number. Positions move, and a pointer that lands on the wrong rule is worse than one that lands on nothing.

    One question at every boundary

    “Is the product wrong, or is the stage being worked wrong?” — answered in writing at every phase or stage boundary. It replaced session budgets, which is what they were for.

    Stopping is a result

    Any stage may end in “stop”. A product whose hypotheses keep failing exits to a write-up: a documented negative result is a legitimate deliverable, and stopping needs only the reason, written down.

    Lessons have an inbox

    Each project keeps a lessons file, written the day something is learned, with the method change it proposes. At the end of every stage I decide each entry; an approved one becomes a rule here. A lesson's text lives in one place at a time — a lesson kept in two places drifts.

    No keys in the repository

    Credentials live in .env only, and nobody — agent or planner — reads, prints, echoes or commits it. Everything else about the process can be published.

    In practice: My Daily News

    The method was rewritten from a week of running it on My Daily News, and that project's documents are public, so every rule above can be checked against the record it came from.

    The prototype phase ran to about thirty sessions where the plan had said a handful; nobody was counting, and the budget mechanism left the method. Phase 2.5 began on 24 September, and its first morning of real use produced ten findings — the morning that showed a freeze needs real use behind it. The tripwire caught a test on its first day, a test whose leftover background work had written two lines into the real log. The measured mornings began on 28 September on a frozen build, re-hashed against a 53-file manifest before each one was accepted.

    The rules held when they were inconvenient. The model's agreement with my own category labels came in at 83.1% against a bar of 85% set in advance; the merge of two categories that would have passed it was declined, because a change chosen to pass a number is chosen for the wrong reason, and the fail stands. The first measured morning was an evening glance of about half a minute, and whether it should count was raised as a fork: three options, each with its costs, and one recommendation — restart the count. I kept the morning instead, because it met every rule written before the data, and discarding a morning because its number looks odd is choosing the rule after seeing the number. The costed options then moved from the specification to the log, because a decided option does not stay in the specification.

    How the method changes

    The method is a document, and it changes the way the products do: from evidence, with the reason written. Every ambiguity met while running it was put to me and settled, in my words where I gave them, and each settlement is recorded next to the rule it produced — “Remove the budget mechanism.” “Ad-hoc backups do not count as valid backups.” “Phase 2.5 falls between Phase 2 and Phase 3; strictly speaking, SPEC.md is written after the product has stabilised.”

    Where it's thin

    It comes from one product's week. The rules were rewritten from what happened on My Daily News. A rule that has run once rests on one data point, and every new project tests the method as much as it uses it.

    It costs calendar time. Stage 2 needs real mornings of use. A missed morning costs a day and a finding costs a restart — the price of a measurement that means something, paid in days.

    One person checks the record. The planning side writes every log, and records its own mistakes next to the coding agent's, but every review ends with me. The method makes a black box less likely; it does not replace a second reviewer.

    It is carried by a document. The method is meant to become a skill, so that a fresh planning session behaves from its first reply the way the planning side did after a week of practice. That work is paused; today the method lives in its document, and in this page.
